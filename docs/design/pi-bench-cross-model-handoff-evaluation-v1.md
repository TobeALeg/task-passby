# 基于 π-Bench 的 Worket 跨模型接力评测方案 v1

日期：2026-09-12
状态：方案已形成，尚未执行；结果章节仅定义输出格式，不包含实验结论。
产品对象：同一个人的同一项工作从来源 Executor 转交给目标 Executor。
候选模型：DeepSeek‑V4.1‑Flash → Qwen3.8，最终型号须先通过能力校准。

## 1. 结论先行

本实验只使用 π-Bench 的任务、workspace、用户模拟与原生 evaluator，不运行 ContinuityBench 数据。ContinuityBench 仅作为“共同前缀、冻结现场、同一断点分叉”的方法参考。

主实验固定为三个条件：

| 条件 | 断点前 | 断点后 | 交接材料 |
| --- | --- | --- | --- |
| A 连续执行 | DeepSeek | DeepSeek | 来源 Executor 保持不变，按原方式继续 |
| B 原文接力 | DeepSeek | Qwen | 完整可见原文、工具记录与同一现场资料 |
| C Worket 接力 | DeepSeek | Qwen | 当前发布版本的 Worket Handoff Package、Work State、Source Archive、ArtifactRef 与标准 MCP 读取路径 |

A、B、C 必须共享同一次 DeepSeek 前序执行和同一个冻结快照。不能为三个条件分别生成前序轨迹。

本实验的主要产品比较是 `C−B`：模型变化和工作中断在 B、C 中完全相同，只改变交接方式。`A−B` 衡量完整原文仍无法消除的模型、执行环境与中断缺口；`A−C` 衡量用户使用 Worket 后仍实际承受的端到端缺口。

## 2. 要回答的问题

### 2.1 主要问题

在真实发生 DeepSeek → Qwen 模型切换和工作中断时，Worket 能否用显著更小、可追溯的交接材料，达到不劣于完整原文传递的后续工作结果？

### 2.2 次要问题

- Qwen 在完整原文条件下，相对 DeepSeek 连续执行还剩多少缺口？
- Worket 是否减少重复询问、重新定位资料、重复已完成动作和误覆写？
- Worket 的按需读取是否能正确找到必要来源，而不是无差别重放全部历史？
- 当 C 失败时，问题来自状态提取、活动产物缺失、来源检索、模型能力，还是目标工具环境？
- Worket 节省的输入 token、费用和恢复时间，是否足以抵偿包生成与按需读取成本？

### 2.3 不回答的问题

- 不评价代码生成或软件工程能力。
- 不把 π-Bench 榜单分数当作 handoff baseline。
- 不声称 11 个合成案例可以代表所有个人知识工作。
- 不测试团队级端到端业务流程替代。
- 不测试同一个工具调用执行到一半时的强制中断；v1 的断点位于自然 session 边界。
- 不把模型隐藏思维或不可见内部状态作为可传递来源。

## 3. 数据来源与版本冻结

数据使用 [π-Bench 官方仓库](https://github.com/Simplified-Reasoning/Pi-Bench)及其 [Hugging Face 任务镜像](https://huggingface.co/datasets/zzzhr97/Pi-Bench)。官方数据为 Apache-2.0，共 100 个任务、5 个个人角色，每个角色 20 个 session；任务包含 hidden intents、难度、任务类型，62 个任务还带可执行或 checklist objectives。每个 persona 的 `episode.yaml` 定义任务顺序和 `depends_on` 关系。

正式运行前冻结并记录：

- π-Bench Git commit SHA；
- Hugging Face dataset revision；
- π-Bench Docker image digest，而不只记录 `latest`；
- AppWorld 数据版本和初始数据库/文件快照 Hash；
- Worket commit、桌面版本、数据库 schema 版本和 Handoff Package 版本；
- 来源模型、目标模型、用户模拟器和 π-Bench judger 的供应商、地域、请求 ID 中的模型标识、参数与日期；
- 每个案例的任务 YAML、依赖闭包、workspace 初始文件 Hash 与 evaluator Hash。

任何上游版本变化都建立新实验批次，不把两个版本混入同一汇总。

## 4. 数据选择

### 4.1 选择原则

正式案例必须同时满足：

1. 目标任务在 `episode.yaml` 中有非空 `depends_on`；
2. 前序任务和目标任务属于同一个明确项目、事项或长期跟踪线程，而不只是把一种写作风格复用于另一个客户；
3. 目标任务要求继续使用前序决定、事实、文件、格式约定或未完成产物；
4. 目标任务有 hidden intents，并有 checklist、文件检查或工具 evaluator；
5. 任务主要产出研究整理、报告、SOP、提案、备忘录、筛选结果、邮件/公开声明或其他 daily desk work；
6. 不要求编写、修复或执行代码；
7. 断点后可以在 π-Bench 的原生工具与 workspace 中继续完成，不依赖真实外部账号。

### 4.2 排除原则

- 排除 Python、PySpark、脚本修复与其他代码任务；
- 排除纯购物、音乐、旅行、健身和与工作无关的个人生活任务；
- 排除只有 persona 级偏好复用、但明显是另一项新工作的链；
- v1 排除 pharmacist 和 law_trainee。它们不是无效数据，但专业正确性和高风险领域差异可能压过 handoff 效应，留作后续外部有效性扩展；
- 排除没有可验收结果或执行环境无法稳定复现的任务；
- 不因某个模型在案例上表现差而事后删除案例。

### 4.3 正式集：11 条依赖链

| Persona | DeepSeek 前序任务 | 目标任务 | 延续的工作 |
| --- | --- | --- | --- |
| marketer | `marketer_task_005` | `marketer_task_006` | Apple × ISSEY MIYAKE 事件资料 → 深度营销分析报告 |

这 11 条链须在看到 A/B/C 结果前完成一次人工语义复核。若某条链实际只是跨工作的方法复用，移入“WorkDefinition 复用”候选集，不进入本次 Handoff 主结果。

### 4.4 Pilot 与正式集

Pilot 只用 4 条 marketer 链，每条 1 个 repeat，共 12 个目标后缀。Pilot 仅检查环境快照、交接材料、工具权限、评分器和盲化是否工作；一旦据此修改协议，Pilot 数值全部作废，不进入最终汇总。

正式集使用 11 条链，每条 3 个独立 repeat。每个 repeat 只生成一次 DeepSeek 前缀，再分叉 A/B/C，共 33 个配对实验块、99 个目标任务后缀。

### 4.5 关于“超长上下文”的边界

π-Bench 的 persona 有 20 个 session，但显式的同项目依赖链通常只有 2–3 个任务。v1 优先保证同一 WorkInstance 的语义正确，不把一个人的全部杂事强行合成一项工作。因此必须实测并报告每条链的消息数、token、文件数和工具事件数；如果没有达到长上下文量级，不得把本实验宣传为超长上下文验证。

完整 persona 历史可以作为后续“个人工作组合迁移”压力测试，但它与当前逐 WorkInstance 交接不是同一产品问题，不混入 v1 的通过/失败结论。

## 5. 模型选择与能力校准

### 5.1 候选

来源模型优先使用 [DeepSeek‑V4.1‑Flash](https://www.deepseek.com/en/news/deepseek-v4-1-flash/)，当前官方 API 名为 `deepseek-flash`。该名称是服务别名，实验必须保存响应返回的实际模型标识，并在同一短时间窗口完成所有配对条件。

目标模型先测试 [Qwen3.8](https://www.alibabacloud.com/help/en/model-studio/web-search) 的日期快照 `qwen3.8-max-0902`；若与来源模型明显不匹配，再按预先顺序测试 `qwen3.8-flash` 或当时可固定的对应日期快照。不得看完主实验结果后更换目标模型。

### 5.2 校准集

从三个正式 persona 中另选 12 个不属于正式链及其前序依赖的非代码 daily desk tasks，每 persona 4 个，按 easy/medium/hard、纯文本/文件/工具任务分层。选择标准和 task ID 在任何模型输出产生前写入 manifest。

DeepSeek 和每个 Qwen 候选都从相同干净快照完整执行这 12 个任务，每个任务 3 次。两者使用相同工具、最大交互轮数、墙钟时间和可见输出预算；模型特有的推荐采样参数分别冻结，隐藏思维不保存、不传输、不评分。

### 5.3 “能力接近”的进入门槛

暂定门槛：

- 平均 COMP 绝对差不超过 5 个百分点；
- 平均 PROC 绝对差不超过 7 个百分点；
- 任一 persona 的 COMP 差不超过 10 个百分点；
- 工具/运行环境失败率差不超过 5 个百分点；
- 没有超过 2/3 的任务呈现同一模型稳定碾压另一模型。

门槛是控制严重能力错配，不是证明两个模型等价。若所有 Qwen 候选均未通过，仍可运行 B/C，因为 B、C 的目标模型相同，`C−B` 仍能评价 Worket；但不得把 `A−B` 主要解释成交接损失，报告必须明确它包含模型能力差异。

### 5.4 版本漂移控制

正式批次开始前后各运行 3 个冻结锚点任务。如果同一模型别名的响应标识变化，或锚点 COMP/行为出现超过预设阈值的突变，停止汇总并重跑受影响的完整实验块。

## 6. 每个案例的前序执行与冻结快照

每个 `case × repeat` 按以下顺序准备：

1. 从同一个 persona 基础快照重置 workspace 和 AppWorld；
2. 只按官方 `episode.yaml` 顺序执行该案例依赖闭包中的前序任务；
3. 前序任务全部由 DeepSeek 完成，使用原始 π-Bench 用户模拟和工具环境；
4. 在目标任务的首条用户消息出现之前冻结；
5. 对快照做完整性检查，再复制为 A、B、C 三个隔离分支；
6. 三个分支收到相同的目标任务、用户模拟器配置、目标 workspace 文件、AppWorld 数据状态、工具权限和预算。

冻结快照至少包含：

- 全部可见用户与 Agent 消息；
- 可见工具调用、参数、返回值与错误；
- workspace 目录树、文件内容 Hash、修改时间和版本；
- AppWorld 数据库/应用状态；
- 前序产物与输入资料清单；
- 模型调用量、时间与停止原因；
- Worket 导入前的来源截止事件序号。

禁止把 hidden intents、objectives、checklist、evaluator 脚本内容、模拟用户私有状态或 `depends_on` 元数据暴露给来源模型、目标模型或 Worket 提取器。

## 7. 三个条件的精确定义

### 7.1 A：DeepSeek 连续执行

- 从共同快照恢复原 DeepSeek Executor；
- 保留其原生可见历史、workspace、工具状态和正常持久化能力；
- 直接执行目标任务直到 π-Bench 原生终止；
- 不生成或注入 Worket Handoff Package。

A 是用户不换 Agent 的连续执行参照，不是对 B/C 的可控单变量实验。

### 7.2 B：Qwen 原文接力

- 创建全新 Qwen 会话；
- 按原顺序提供截止断点前同一 WorkInstance 的全部可见用户消息、DeepSeek 回复、工具调用与可见结果；
- 原始文件正文不因为“原文传递”而额外塞入 Prompt，但 Qwen 可以访问与 A/C 完全相同的现场文件和 AppWorld 状态；
- 附带一个中性边界说明：以上是前任执行者的可见工作记录，请继续同一项工作；
- 不提供 Work State、Handoff Package 或任何模型生成摘要；
- 随后注入目标任务的同一首条用户消息并正常运行。

B 是“可传递可见原文”的高保真基线，不是假设 Qwen 获得 DeepSeek 隐藏思维、私有缓存或不可导出的应用内部状态。

若 B 超过目标模型上下文限制，不得静默截断。该案例标记为 `RAW_CONTEXT_OVERFLOW`，另报“最大可输入原文”结果；它不能继续被称为完整原文基线。

### 7.3 C：Qwen 经 Worket 接力

- 使用与 B 相同的新 Qwen 会话、快照、工具、预算和目标消息；
- 把前序可见记录通过当前 Worket 正式记录路径写入一个 WorkInstance/WorkRecord；
- Source Archive 仅包含用户已授权、Agent 可见的来源事件；
- 前序输入和产物按当前实现生成 ArtifactRef，并在交接前复核 Hash 与可用性；
- 使用当前发布版本和冻结配置更新八部分 Work State，生成不可变 Handoff Package；
- 目标会话收到当前产品的标准交接首条指令和 WorkInstance ID，通过标准 MCP 获取 `get_work_context` 及现有来源/资料读取能力；
- 主 Prompt 不额外拼接完整 Source Archive；不人工补写遗漏字段，不针对单个案例调整包；
- 记录 Qwen 实际读取了哪些 Work State、来源事件和 ArtifactRef，以及首次有效动作前的恢复过程。

C 测的是当前 Worket 整体交接路径，不只是八字段摘要。如果 Qwen 环境不能真实调用 Worket MCP、读取 Source Archive 或解析 ArtifactRef，则停止实验；把摘要复制进 Prompt 的替代实验只能标记为“离线表示测试”，不能声称完成产品级 C 条件。

## 8. 公平性控制

B、C 必须固定：

- 同一个 Qwen 模型版本、地域、采样参数和 system policy；
- 同一目标用户消息和同一用户模拟器版本；
- 同一 workspace/AppWorld 快照；
- 同一工具集合、权限、最大步骤、输出上限和墙钟预算；
- 同一网络可用性与搜索接口；
- 同一目标任务 evaluator；
- 配对的随机 seed 与随机运行顺序。

A 与 B/C 的不同只用于呈现真实换模型的端到端缺口。任何“为了让 Worket 更好用”而给 C 额外工具、更多时间或更高输出预算的做法都会使主比较失效。

API/工具瞬时失败按预先规则最多重试两次；内容质量差、错误工具选择和模型自行提前结束不得重试。快照 Hash 不一致时废弃整个配对块并从前序重新生成，不能只重跑较差条件。

## 9. 交接契约与金标准

在运行 A/B/C 目标后缀之前，根据官方任务、可见前序记录和冻结现场，为每个案例建立一份不暴露给模型的交接契约：

- `MUST`：接手后必须掌握的目标、约束、决定、已完成动作、下一步和必需资料；
- `ON_DEMAND`：无需预先注入，但执行到相关环节时必须能够找到；
- `MUST_NOT_ACTIVATE`：已撤销、替代、否定或仅探索过的内容；
- `NEW_DECISION_REQUIRED`：来源中没有答案，应该询问而不能猜测。

每项保留来源事件/文件证据，标记关键 `5`、重要 `2`、辅助 `1`。契约先冻结，再生成 C 包和目标输出，不能依据某个条件的失败反向调整 gold。

π-Bench hidden intents 和 checklist 保持原样，交接契约只补充 continuity 诊断，不替换官方 evaluator。

## 10. 评测体系

### 10.1 原生主结果

[π-Bench](https://simplified-reasoning.github.io/Pi-Bench/) 的两个原生指标保持权威：

- `PROC`：Agent 主动完成或通过有针对性的澄清识别 hidden intents 的比例；
- `COMP`：完整轨迹、工具记录和最终产物满足 checklist 的比例。

主要质量结论先看 COMP，再看 PROC。不能用回答相似度或模仿 A 的措辞代替任务验收。

### 10.2 Worket 连续性评分

由助手在不知道 A/B/C 标签和模型身份的情况下，按冻结契约评 0–100：

| 维度 | 权重 | 判断内容 |
| --- | ---: | --- |
| 目标与约束保持 | 30 | 是否保留 MUST 目标、用户约束和已确认决定 |
| 进度连续性 | 20 | 是否从正确下一步开始，避免重新做已完成工作 |
| 产物与资料续用 | 20 | 是否使用正确文件、版本和前序产物，而非重新臆造 |
| 状态新鲜度 | 15 | 是否避免激活已撤销、过期或冲突信息 |
| 澄清质量 | 10 | 是否只询问真正未知事项，避免让用户重述已有信息 |
| 来源可核验性 | 5 | 关键结论和动作能否回到正确来源 |

任何关键权重 5 项被违反时，标记 `critical_failure=true`，不能被低价值项目平均抵消。

### 10.3 恢复与成本指标

不把成本过早折成单一总分，分别报告：

- `C_prepare`：Worket 整理输入/输出 token、调用次数、费用和包生成延迟；
- `C_ingest`：首次注入 token、MCP/来源/资料读取量、首次有依据有效动作前的步骤和时间；
- `C_repair`：重复询问、纠正、撤销、重做、额外工具调用与最终验收时间；
- 总输入/输出 token、总调用费用、墙钟时间；
- 首版通过率、固定预算内最终通过率、每个通过案例成本。

B 的原文 token 与 C 的首条包加后续按需读取 token 都计入目标端总输入，不能只比较首条 Prompt 长度。

### 10.4 盲评方法

1. 先冻结 rubric、交接契约和评分表；
2. 目标后缀随机编号为 X/Y/Z，隐藏条件、模型、包类型和供应商元数据；
3. 第一阶段只向助手提供目标任务、gold、规范化后的目标期行为和最终产物；上下文注入文本与带有 `get_work_context` 名称的机制线索不展示；
4. 助手锁定质量分、关键错误和理由；
5. 第二阶段揭盲，查看完整来源读取与工具轨迹，只做故障归因和成本分析，不反改盲评分；
6. π-Bench 原生 evaluator 独立运行，最终报告同时给出原生分和助手评分，不把两者伪装成多人一致性。

可在盲评批次中随机插入 20% 重复样本，检查助手自身评分稳定性；重复样本不增加统计样本量。

## 11. 效应量与统计

设 `S` 分别表示 COMP、PROC 或连续性分数：

- 最佳原文下的换手缺口：`G_switch = S(A) − S(B)`；
- Worket 相对原文的变化：`G_worket = S(C) − S(B)`；
- Worket 端到端缺口：`G_end = S(A) − S(C)`。

每个 `case × repeat` 是一个配对块。统计时先对同一案例的 3 个 repeat 取均值，再以 11 个案例为独立单位；不能把 33 个 repeat 当成 33 项不同真实工作。

每个效应至少报告：

- 配对平均差和中位差；
- 11 个案例中胜/平/负数量；
- 按案例聚类的 95% bootstrap 置信区间；
- marketer、Financier、researcher 分层结果；
- 一前序任务/两前序任务、文本/文件/工具、上下文 token 和资料数量分层；
- critical failure 的案例级绝对数量，不只报百分比。

样本只有 11 条独立链，统计功效有限。置信区间过宽时应报告“方向未确定”，不能用 3 次 repeat 冒充更大的任务样本。

## 12. 预先决策门槛

### 12.1 Worket 通过 v1

C 相对 B 同时满足：

- COMP 平均下降不超过 5 个百分点；
- 连续性分平均下降不超过 5 分；
- critical failure 不比 B 多超过 1 个案例；
- 并且至少满足一项：目标端总输入 token 降低 30%，`C_ingest + C_repair` 步骤降低 20%，或首版通过率提高 10 个百分点。

以上是探索期产品门槛，不是统计显著性声明。正式结论同时给出区间和逐案例结果。

### 12.2 强通过

满足普通通过，并且 C 的 COMP/连续性显著高于 B，或在质量非劣前提下将目标端总输入降低至少 50%，且不增加 critical failure。

### 12.3 未通过

出现任一情况：

- C 相对 B 的 COMP 或连续性下降超过预定非劣界；
- C 明显增加关键遗漏、错误激活、误覆写或重复工作；
- token 虽减少，但恢复与返工使总机器成本或总时间更高；
- 优势来自 C 获得了 B 没有的现场状态、工具权限或预算；
- C 不是通过真实 Worket 路径生成和读取。

## 13. 失败分类

每个失败至少归入一种，允许多标签：

- `DEPENDENCY_OMISSION`：漏掉前序任务必须继承的信息；
- `STALE_ACTIVATION`：使用已撤销或过期状态；
- `GOAL_DRIFT`：偏离同一 WorkInstance；
- `PROGRESS_RESET`：重复前任已经完成的工作；
- `ARTIFACT_MISS`：未找到所需资料或前序产物；
- `WRONG_VERSION`：使用错误文件/产物版本；
- `DESTRUCTIVE_OVERWRITE`：错误覆盖现场成果或状态；
- `OVER_CLARIFY`：要求用户重述来源中已有内容；
- `UNDER_CLARIFY`：对真正未知的新决定擅自猜测；
- `UNSUPPORTED`：把来源中不存在的信息当作已确认事实；
- `TOOL_ENVIRONMENT`：工具、权限、应用状态或适配器差异导致失败；
- `MODEL_CAPABILITY`：信息已充分提供但目标模型仍无法完成；
- `RAW_CONTEXT_OVERFLOW`：完整原文超过目标上下文；
- `TRUNCATION`：输出或轨迹因长度/时间预算终止；
- `EVALUATOR_FAILURE`：原生 scorer 或盲评材料不完整。

揭盲后的归因必须引用具体消息、文件 Hash、工具步骤或 evaluator 证据，不能只凭主观印象。

## 14. 执行阶段与停止条件

### 阶段 0：预注册

- 冻结本文、数据 manifest、11 条链、交接点、模型候选顺序、参数、预算、rubric 和门槛；
- 建立结果目录与条件映射的访问隔离；
- 不生成任何正式 A/B/C 输出。

### 阶段 1：环境与模型预检

- 核实版本、API 可用性、上下文上限、工具调用和 Qwen 对 Worket MCP 的真实访问；
- 验证 AppWorld/文件快照能被复制且 Hash 一致；
- 计算两条案例的实际 token、时间和成本，形成正式预算估算并预留 20% 重试余量。

### 阶段 2：能力校准

- 完成 12 个校准任务 × 2 个模型 × 3 次；
- 选定并冻结 Qwen 型号；
- 若未找到相近模型，保留 B/C 但降低 A 比较的解释强度。

### 阶段 3：Pilot

- 跑 4 条 marketer 链 × 1 次 × A/B/C；
- 只检查协议和评分材料，不发布产品结论；
- 若修改任何规则，重新冻结并废弃 Pilot 分数。

### 阶段 4：正式运行

- 跑 11 条链 × 3 个 repeat；
- 每个 repeat 生成一次 DS 前缀和一个快照，再随机顺序执行 A/B/C；
- 保存全部成功与失败轨迹，不挑选“正常发挥”的结果。

### 阶段 5：评价与揭盲

- 先运行 π-Bench 原生 evaluator；
- 再把规范化的匿名材料交给助手盲评；
- 锁定评分后揭盲，完成成本和失败归因；
- 生成逐案例、分层和总体报告。

出现下列任一情况立即暂停正式汇总：

- 模型 alias 或 Docker/AppWorld 版本中途变化；
- B、C 不能从同一快照恢复；
- evaluator、hidden intent 或 checklist 泄漏给实验模型；
- Qwen 无法真实使用 Worket 标准读取路径；
- 有效正式案例少于 9 条；
- 条件间工具、权限、预算或目标消息不一致；
- 原生 evaluator 无法稳定重放关键产物/工具状态。

## 16. 结果解释矩阵

## 18. 当前边界

本方案完成的是评测设计，不是实验结果。当前不能声称：

- DeepSeek‑V4.1‑Flash 与某个 Qwen3.8 型号已经能力相当；
- Worket 已达到原文传递质量；
- Worket 已减少 token、返工或用户时间；
- 当前 Worket 已支持 DeepSeek 与 Qwen 的真实桌面 Adapter；
- π-Bench 的 11 条依赖链构成超长上下文或真人工作证据。

只有完成版本冻结、模型校准、真实 MCP 接力、原生 evaluator、盲评和揭盲统计后，才能依据第 12 节门槛给出通过、未通过或方向未确定的结论。
