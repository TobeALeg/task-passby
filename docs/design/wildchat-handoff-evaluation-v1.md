# WildChat 跨模型交接评测方案 v1

状态：研究设计，尚未下载数据、调用模型或形成实验结论。
日期：2026-09-12

## 1. 研究问题

本实验使用 WildChat 中由 GPT-4o 产生的长程真实用户对话，在自然的后段位置人为插入交接点，将同一项工作交给一个中国模型继续。

需要依次回答两个问题：

1. **模型变化的影响**：接收模型在拥有完整历史时，与数据中原 GPT-4o 的自然续答相比，是否处于相近的执行能力带？
2. **交接表示的影响**：接收模型固定后，只改变它看到的交接上下文，工作结果相对完整历史损失多少；不同交接方法之间有何差异？

这两个问题不能混合。若接收模型与 GPT-4o 能力差异很大，直接比较原回复与交接后回复，无法归因于交接质量。

WildChat 没有文件、工具状态和真实交付验收。本实验中的“执行结果”特指：新模型面对原对话中下一条真实用户请求时，给出的续答能否延续此前形成的目标、约束、决定与风格。它不是 Worket 完整产品交接收益的最终证明。

## 2. 数据与模型边界

### 2.1 数据版本

使用 [WildChat-4.8M](https://huggingface.co/datasets/allenai/WildChat-4.8M) 的公开非有害内容版本，固定下载快照、分片哈希和筛选代码版本。只选择原始 `model` 字段属于 GPT-4o 的记录，不混入 GPT-3.5、GPT-4.1-mini、o1 或其他模型。

WildChat 并不是基于“GPT-5.3/5.4”生成。原始论文版本主要是 GPT-3.5-Turbo 与 GPT-4；后续 4.8M 版本包含 GPT-4o、GPT-4.1-mini、GPT-3.5-Turbo、GPT-4、o1 等模型。当前数据卡记录 GPT-4o 家族约 1,539,780 份，数量足以进一步筛选长对话。

### 2.2 接收模型候选

第一候选改为阿里云百炼北京地域的 `deepseek-v3` 非思考模型：

- [阿里云当前文本模型清单](https://help.aliyun.com/zh/model-studio/model-list-text-generation/)仍明确列出该模型，且有独立的[模型信息页](https://help.aliyun.com/zh/model-studio/deepseek-v3)，比只残留旧说明页的模型更容易确认实际可调用状态；
- 模型为 2024 年 12 月发布的初代 DeepSeek-V3，时间和 GPT-4o 子集较接近；DeepSeek 当时公布的多项评测把它定位为与 GPT-4o、Claude 3.5 Sonnet 相近的能力带。这仍是厂商结论，只用于形成候选；
- 通过中国境内阿里云账号取得 API，模型 ID 为 `deepseek-v3`；上下文 65,536，最大输入 57,344，最大输出 8,192，足以覆盖本方案筛选后的 WildChat 对话；
- 页面当前列出的北京地域原价为输入 2 元/百万 Tokens、输出 8 元/百万 Tokens。

第一备选为阿里云百炼当前仍列出的 `qwen-max`。其当前说明页称运行版本功能等同于 `qwen-max-2025-01-25`，Qwen 发布材料曾将 Qwen2.5-Max 与 GPT-4o 并列比较；但日期快照端点已经下线，`qwen-max` 是可能滚动更新的主线别名，所以只有在同一批次内完成实验并通过锚点漂移检查时才使用。

`GLM-4-Plus` 不再作为已确认可调用的首选。它仍有[旧系列说明页](https://docs.bigmodel.cn/cn/guide/models/text/glm-4)，但未出现在智谱[当前模型总览](https://docs.bigmodel.cn/cn/guide/start/model-overview)的全部文本模型中；除非实验开始前通过模型列表查询和最小测试调用证明账号仍可访问，否则不进入候选池。也不使用 DeepSeek 原厂当前 V4 系列、GLM-5.x、Qwen3.x 等明显更晚的模型作为首轮接收者，以免强模型掩盖交接信息损失。

### 2.3 API 可用性预检

在下载大规模样本或开始人工标注前，对候选逐一执行：

1. 从服务商当前模型列表确认模型 ID，而不是依据搜索引擎仍可访问的旧详情页；
2. 使用实验账号做一条最小 Chat Completions 调用，保存 HTTP 状态、响应 `model` 字段、日期和服务地域；
3. 用一条长历史测试实际输入上限，用一条定长请求确认输出上限；
4. 冻结服务商、地域、模型 ID、调用参数和实验日期；若模型别名滚动更新，立即停止跨版本混跑。

预检只证明“当前可调用”，能力是否接近 GPT-4o 仍由第 6 节的实测校准决定。

## 3. 样本筛选

### 3.1 自动筛选

从 GPT-4o 子集中筛选：

- `turn >= 9`，优先 9–20 轮；
- 中文或英文，主实验各占一半；
- `toxic=false`、`redacted=false`；
- 没有空用户消息、明显个人信息、密钥、违法内容或高风险医疗/法律请求；
- 对话主要围绕同一项持续工作，不是问答拼盘、纯角色扮演或越狱；
- 至少有一次用户补充、纠正、否定、改写、选择方案或引用前文；
- 后段至少有一条用户请求必须结合更早历史才能正确回应。

先流式筛出 2,000–5,000 条候选，不完整下载 15.3 GB 数据。自动分类只能缩小范围，不能最终判断“同一项工作”。

### 3.2 人工筛选

两名审阅者独立判断 150–200 条候选，保留 60 条正式案例：

- 中文 30、英文 30；
- 写作/改写、分析/决策、编码/技术说明各至少 15 条，其余为其他连续工作；
- 长度、原模型具体标识和主题尽量分层；
- 不按原 GPT-4o 回复“看起来好不好”选择，避免只保留原模型成功案例。

分歧由第三次复核解决。只保存上游 ID、标签和选择理由到 manifest；聊天正文保存在仓库外的本地受控目录。

## 4. 交接点

对每个案例选择一个自然交接点 `k`：

- 至少保留前 7 轮作为已发生工作；
- 至少保留后 2 轮作为未见数据；
- 对 9 轮对话，默认在第 7 轮助手回复后交接；
- 更长对话优先在总轮数的 70%–85% 处，但必须是一个自然阶段边界；
- 第 `k+1` 轮用户消息作为所有实验条件共同收到的真实继续请求；
- 第 `k+2` 轮用户消息只作为理解用户后续反馈的审阅证据，不直接喂给模型。

只做一次续答可以避免轨迹分叉：若候选模型在第 `k+1` 轮给出了不同回复，原来的第 `k+2` 轮用户消息未必仍然合理，不能强行继续回放并声称是真实对话。

## 5. 交接契约

在生成任何实验输出前，两名审阅者仅依据第 1 至 `k` 轮建立金标准：

- 当前工作目标；
- 当前用户请求必须继承的约束；
- 用户已确认的决定；
- 已被撤销、替代或否定的旧信息；
- 已完成内容与当前进度；
- 用户希望保持的格式、语言和表达风格；
- 第 `k+1` 轮必须结合哪些前文才能正确回答；
- 哪些问题来源中没有答案，模型应当澄清而不是猜测。

每项标记关键 `5`、重要 `2`、辅助 `1`，并保留来源轮次。第 `k+2` 轮只能帮助审阅者发现遗漏的真实偏好，不能用于修改成对某个实验输出有利的标准；任何补充都需单独标记为“后见证据”。

## 6. 第一阶段：接收模型能力校准

先随机选择 30 个案例，只运行完整历史条件：

| 编号 | 输出 | 作用 |
| --- | --- | --- |
| R0 | WildChat 中原 GPT-4o 对第 `k+1` 轮的真实回复 | 历史参考，不假定为标准答案 |
| R1 | 阿里云百炼 `deepseek-v3` 读取第 1 至 `k` 轮完整历史后，对同一第 `k+1` 轮请求的回复 | 测量接收模型能力 |
| R2 | 备选模型在相同完整历史下的回复，仅在 R1 未通过校准时运行 | 选择替代接收模型 |

所有模型使用相同中性 system prompt、无工具、无联网；保持原对话语言。接收模型固定 `temperature=0.2`、固定输出上限，每案例独立运行 2 次。记录服务商、地域、请求模型 ID、响应返回的模型标识、日期和参数；若服务只提供可变 alias，每批开始重跑 10 条锚点案例检测漂移。

### 6.1 校准评分

审阅者不知道回复来自哪个模型，按以下维度各评 0–4 分：

- 任务完成度 35%；
- 对前文关键目标/约束的遵守 30%；
- 与当前进度的连续性 20%；
- 无依据内容与事实风险 15%。

另做 R0/R1 盲配对，记录 R1 胜、平、负。原回复不是 gold，因此不按文字相似度评分。

`deepseek-v3` 进入主实验的暂定门槛：

- 与 R0 的平均总分差绝对值不超过 5/100；
- R1 相对 R0 的胜率和负率都不超过 60%，即没有明显单向碾压；
- 关键约束错误率差不超过 5 个百分点；
- 中文和英文分层均未出现超过 10 分的系统性差距。

若未通过，不调参到“恰好过线”；改测备选模型。若所有中国 API 模型都明显强于或弱于 GPT-4o，则保留差异并把模型作为实验因子，而不是宣称找到了等价模型。

## 7. 第二阶段：完整历史与交接方法比较

接收模型固定后，在全部 60 个案例上运行：

| 条件 | 接收模型获得的上下文 | 回答的问题 |
| --- | --- | --- |
| H0 完整历史 | 第 1 至 `k` 轮原始可见对话 | 同一接收模型在“无信息损失”时能做到什么；这是主要对照 |
| H1 最近窗口 | 最近 2 轮原始对话 | 简单截断能做到什么 |
| H2 当前 Worket | 现有八部分 Work State、当前任务、下一步及可追溯来源标识 | 当前交接方案损失多少 |
| H3 候选方法 | 新的交接组织方法 | 新方法是否优于 H2 |
| H4 人工最小包 | 人工整理的最小充分上下文，仅在 20 条子集运行 | 估计压缩后的可达上限 |

每个条件都在全新、无记忆的 API 请求中运行，之后追加完全相同的第 `k+1` 轮真实用户请求。条件名称和包生成方式对接收模型与审阅者隐藏。每个“案例 × 条件”运行 2 次，随机化顺序。

H0 虽然也是一次新 API 调用，但在无状态 Chat API 中，“继续原聊天”本来就是重新发送完整历史；因此它是控制接收模型不变时最接近“未发生交接信息损失”的条件。

## 8. 三个独立效应量

设 `S(x)` 为盲审后的 0–100 工作结果分：

```text
模型差异       G_model  = S(H0) - S(R0)
方法交接损失   L_method = S(H0) - S(Hmethod)
方法增量       G_method = S(H3) - S(H2)
```

- `G_model` 回答换成中国接收模型本身带来什么变化；
- `L_method` 回答把完整历史变成交接表示损失多少；
- `G_method` 才回答新交接方法是否比当前 Worket 更好。

不能用 `S(H2)-S(R0)` 直接评价 Worket，因为它同时包含模型变化与交接变化。

## 9. 结果指标

### 9.1 主要结果

- 工作结果总分；
- 严格通过率：总分至少 80，且没有关键项错误；
- 关键目标/约束错误率；
- 相对完整历史的非劣性；
- 用户已有信息被重复询问的比例。

### 9.2 交接诊断

- 加权 `MUST` 信息召回率；
- 已撤销信息错误激活率；
- 目标漂移、进度倒退和重复已完成工作的比例；
- 语言、格式和风格连续性；
- 无依据新增事实率；
- 正确澄清未知事项与多余澄清的比例。

### 9.3 成本

- 交接包生成输入/输出 token、费用和延迟；
- 注入接收模型的上下文 token；
- 接收模型输出 token、费用和延迟；
- 每取得一个严格通过案例的总 token 和 API 成本；
- 人工标注与审阅分钟数。

WildChat 没有真实用户在交接后的操作，不能在本实验中报告用户实际重复说明时间或返工分钟数。

## 10. 评分与统计

- 两名真人独立评分；主结果取平均，关键错误分歧必须复核；
- 先报告评分者一致性，再报告模型结果；
- LLM judge 只用于发现可能遗漏和排序待复核案例，不作为最终裁判；
- 以案例为配对单位，报告 H2-H0、H3-H2 的平均/中位差与 95% bootstrap 置信区间；
- bootstrap 按 conversation 聚类，同一案例的两个模型输出不能当作两个独立工作；
- 中文/英文、任务类型、轮数和交接契约复杂度分层报告；
- 失败和截断输出不删除，按预先规则计分。

### 10.1 决策门槛

当前 Worket H2 被视为有效压缩的暂定条件：

- 相对 H0 的工作结果下降不超过 5 分；
- 严格通过率下降不超过 5 个百分点；
- 关键错误率不增加超过 2 个百分点；
- 上下文 token 至少减少 30%。

候选 H3 优于 H2，须满足关键错误不增加，并至少满足一项：

- 平均工作结果提高至少 5 分；
- 严格通过率提高至少 10 个百分点；
- 在结果非劣的前提下，上下文 token 或总 API 成本再降低至少 20%。

这些是探索期门槛，不是统计显著性或产品承诺。

## 11. 失败分类

每个失败至少归入一类：

- `OMISSION`：遗漏有效要求；
- `STALE_ACTIVATION`：把已撤销内容当成当前决定；
- `ATTRIBUTION`：把 Agent 建议误当用户要求；
- `GOAL_DRIFT`：偏离当前工作；
- `PROGRESS_RESET`：重复已经完成的内容；
- `UNSUPPORTED`：编造来源中没有的事实；
- `OVER_CLARIFY`：要求用户重述已有信息；
- `UNDER_CLARIFY`：对真正未知的决定擅自猜测；
- `STYLE_BREAK`：破坏用户已经形成的格式、语言或风格要求；
- `TRUNCATION`：长度、API 或上下文限制导致结果不完整。

## 12. 隐私、许可与复现

- 遵守 WildChat 的 ODC-BY 署名与数据库许可要求；公开派生数据前另做许可审查；
- 立即丢弃国家、州、哈希 IP、请求头、原始模型请求 ID等非必要字段；
- 再运行本地 PII、凭据和敏感内容扫描；
- 正文不进入 Git、BP 文档或模型服务日志；
- manifest 只保存数据版本、会话哈希/轮次 ID、筛选标签、交接点、许可与结果位置；
- 原文与模型输出放在 `output/` 下的受控实验目录，沿用仓库忽略规则；
- 保留上游删除检查机制；被删除的会话从后续实验和可复现包中撤下；
- API Key 只通过环境或密钥存储读取，不写入配置、日志或结果。

## 13. 执行顺序与停止条件

1. 写流式筛选器并人工确认 30 条校准集；
2. 完成候选 API 可用性预检，运行 `deepseek-v3` 完整历史校准；
3. 通过则冻结模型与参数；不通过则测试备选模型；
4. 扩充到 60 条正式集并完成交接契约；
5. 先跑 H0/H1/H2，验证评分和埋点稳定；
6. 冻结 H3 方案后再运行，禁止看完 H2 失败再逐案例改 H3；
7. 输出配对结果、成本前沿和失败案例，不先输出单一总分；
8. 若真人一致性不足、接收模型未通过校准、有效案例少于 40 或 API alias 中途升级，停止主实验并修复设计，不继续汇总结论。

首轮正式实验预计：校准 30 个案例 × 2 次；主实验 60 个案例 × 4 条主要条件 × 2 次，共约 540 次接收模型调用，另加交接包生成调用。实际费用在筛选出样本并统计 token 分布后计算；人工交接契约与盲审预计是主要成本。
