## B001 — 工作授权与可替换执行者

### 讨论起因与用户观点

讨论 Zep 的项目隔离、RBAC、API Key ABAC 和 UserGroup 后，用户认可项目隔离可能必要，担心把 Agent 当成固定岗位或角色逐一配置权限，会让组织在引入、升级、拆分或合并 Agent 时不断维护角色与授权。用户提出：这种随 Agent 能力变化而调整角色的方式，可能难以满足 AI-native 组织的灵活性。

记录其核心问题：企业如何持续吸收更强的 AI 执行能力，同时避免每次调整执行者都重新配置组织权限？上述复杂度判断是用户提出的设计问题，尚不能据此断言 Zep 无法支持 AI-native 组织。

### 已核实的竞品事实

核实日期：2026-09-10；范围：Zep v3 官方文档。

- 普通 API 请求按 API Key 所绑定的策略授权。一份策略集可以绑定多个 Key，一个 Key 可以绑定多份策略集；其 `role` 指 `default_allow` / `default_deny` 两种初始权限立场，不等于为每种 Agent 能力建立业务岗位。
- 文档没有要求每个 Agent 另建终端用户，也没有要求每新增或升级一个 Agent 都新增角色或策略。权限配置成本取决于调用方如何管理身份、凭据与策略绑定。
- UserGroup 当前治理 Memory MCP 用户对共享独立图谱的访问，普通 API Key 流量不受用户组策略影响。后台人员的 RBAC 是另一条管理路径。

来源：[Agent access](https://help.getzep.com/attribute-based-access-control)、[UserGroup access](https://help.getzep.com/usergroup-access)、[Managing team access](https://help.getzep.com/role-based-access-control)。

### 对 Worket 的洞察

工作的目标、责任和授权范围通常比承担工作的具体 Agent 更稳定。如果权限主要围绕某个长期固定的 Agent 岗位配置，执行分工变化可能带来额外维护；可以探索让具体工作的授权约束保持稳定，由可替换执行者在该范围内承担执行。

当前项目依据：[CONTEXT.md](../../CONTEXT.md) 已将 WorkInstance、Executor 和 ExecutionEpisode 分离，交换执行者不改变工作身份；[产品文档](../product.md) 与 [架构文档](../architecture.md) 描述了这一接力基础。现有材料不能证明 Worket 已实现企业级动态工作授权。

### 助手提出的设计设想（待讨论，未批准实现）

保留组织、项目和资源边界；由有权委托的人或组织为本次 WorkInstance 确定允许访问的资料、操作、期限和责任。执行时，系统结合当前策略与执行环境约束签发受限授权，并记录本次执行者。授权由可信应用执行，不由模型自行声明。

更换执行者时，在工作范围不变的前提下重新校验并签发授权，尽量复用已有约束，不要求业务人员为每种 Agent 能力手工建立永久岗位。新增数据、操作或委托范围仍须重新授权；Agent 更强不意味着权限自动扩大。新执行环境的身份接入与信任检查仍然必要。

工作定义可表达授权需求，但下一次复用不能继承上次的临时授权或客户访问权；这一边界与现有“本次输入”约定一致。撤销只能阻止后续访问，不能保证收回已交给外部执行者的数据。

### 用户价值与 BP 候选表达

潜在价值：企业可以持续更换、组合或升级 AI 执行者，同时减少重复权限配置，并保留工作责任与审计连续性。配置成本是否下降，需要实际比较。

候选表述（方向性，不能作为当前能力宣传）：**Worket 希望让企业围绕工作保持责任与授权边界，在边界内持续升级 AI 执行方式，降低组织吸收新能力的调整成本。**

### 可展示场景与验证要求

以“为客户 A 准备报价草案”为例：工作允许读取客户 A 的指定资料并生成草稿，发送报价需要单独批准。先由 Agent A 执行，再换 Agent B，或拆给两个执行者协作；工作身份和验收标准保持不变，各执行者仅获得其执行范围内的授权。

待验证：换执行者需要多少次人工配置；拆分任务是否能限制子任务权限；旧授权是否失效；客户 B 的资料是否不可访问；发送操作是否仍需批准；能否追溯委托人、执行者、授权版本与操作结果。应与复用策略或自动绑定策略的方案比较，不能只与“每个 Agent 手工新建角色”的低效配置比较。

尚缺证据：企业用户是否实际遇到这一成本，当前 Worket 是否能端到端执行上述约束，以及它相对其他方案带来的可量化收益。

## B002 — 用后续工作的交付效果验证沉淀价值

### 讨论起因与研究事实

用户要求解读 MemOp；本条是助手据此提出的产品洞察，尚未经过用户确认。

2026-09-10 核实：[项目页](https://xhguo7.github.io/MemOp/)、[论文 v1](https://arxiv.org/html/2606.05646v1)、[官方代码说明](https://github.com/xhguo7/MemOp)。MemOp 将执行轨迹转成记忆候选，用有无记忆的执行结果筛选候选，再训练独立的记忆生成模型。它评估单次轨迹再利用与跨任务记忆演化；主要验证范围是 Python 仓库中的软件修复任务。

### 对 Worket 的洞察与当前依据

沉淀的内容是否忠实、用户是否确认，以及下一次使用是否改善交付，是三个不同问题。确认适合保存的工作定义，不等于证明它能减少返工或提高交付质量。应将后续复用与验收反馈关联回定义版本，才有依据决定哪些抽象值得保留、修订或停止推荐。

当前依据：[产品文档](../product.md) 已要求第二次真实执行验证，并描述了来源、候选、人工修改、定义版本、复用和验收反馈的采集链；同一文档明确真实样本版本效果比较尚未完成。这是评测基础，不是收益证据。研究记忆也不等于 WorkDefinition；工作约定、原始记录和执行经验仍须区分。

2026-09-10 补充：用户询问开发者能否获得使用者与 AI 的聊天记录；这一问题不代表授权新增采集。当前代码核实：普通记录保存在使用者本机；沉淀所选材料经过配置的后台与模型供应商处理，但只有另行勾选“参与改进 Worket”才进入管理员可查看的样本库，授权起保存 90 天。客户端必须连接该管理员管理的服务并成功同步，安装应用本身不等于上报。依据：[桌面授权与样本登记](../../src/distillation/desktop.ts)、[服务连接](../../src/ai-service/client.ts)、[改进样本说明](../../server/README.md)。本次未核实线上部署或真实用户样本到账情况。

2026-09-10 用户后续明确：非常需要真实使用情况作为后续优化的数据基础，要求参与改进默认勾选、直到用户取消，并希望安装后直接连接后台；随后将交付边界调整为先修改，不发布、不打包，待前端优化后再打包。默认偏好与停止行为本轮修改源码；自动接入仍待确定后台地址和首次身份接入方式，不能表述为真实样本已经自动到账。此前“另行勾选”描述对应旧版行为。

助手补充的价值判断（待验证）：产品改进的评测价值取决于授权材料能否关联候选、人工修订与后续验收，不能用聊天记录总量代替质量证据。可展示同一授权样本从来源到修订、验收的过程及停止、删除入口；真实覆盖率、反馈质量和改进收益仍须试点验证。本条不增加授权范围或批准训练。

2026-09-10 部署补充：根据用户提供的 VPS，已实现独立安装自动接入并实测可信 HTTPS、六类合成事件收集、管理员查看、跨安装隔离、停止与删除；桌面取消选择重启后保持。后台上线与桌面发布独立进行，当前未打包发布、模型配置待授权，不能表述为真实用户数据或改进收益已经取得。证据：[VPS 部署验收](../deployment/vps-operation.md)、[实时数据链路脚本](../../scripts/qa-vps-samples.mjs)。助手提出的价值方向：减少参与改进的连接配置成本，同时保留可追溯的安装身份和退出控制；是否提高真实反馈覆盖率仍待试点验证。

2026-09-11 状态更新：用户明确同意模型 Key 迁移，已完成 VPS 加密配置及真实 DeepSeek 调用验收。合成周报案例从真实模型候选、修改发布到复用和合成成果验收形成六类事件回传；停止、删除、客户端和服务端重启恢复均通过。该结果验证了数据闭环可运行，尚不证明真实用户覆盖率、真实第二次交付或改进收益；初次失败暴露的目标字段格式和引用片段问题已通过明确提示修复，契约校验没有放宽。证据：[真实模型验收记录](../deployment/vps-operation.md)、[桌面公网脚本](../../scripts/qa-vps.mjs)。

2026-09-11 采集覆盖边界复核：用户询问新版能否把使用者对话上传服务器。当前代码支持沉淀时将所选对话材料及后续修订上传改进样本库；复用仅回传定义、非文件输入和验收反馈，不回传新工作对话。普通记录没有通用对话上传入口，默认参与改进不等于全部聊天自动同步。本轮公网 `/health` 实测返回 `ok:true, configured:true`；GitHub 最新发布仍为 2026-09-09 的 `v0.1.1`，部署记录明确新版桌面未打包发布。已有合成材料闭环证明链路可运行，真实用户到账仍未验证。产品判断：若优化需要普通记录中的对话样本，当前沉淀触发机制的覆盖率是否足够须单独验证；本次询问不代表批准扩大采集范围。依据：[采集触发](../../src/distillation/desktop.ts)、[用户范围说明](../../src/renderer/distillation.ts)、[部署记录](../deployment/vps-operation.md)。

### 待讨论的验证方法

选择同一类重复工作，用新输入比较“原有方式、普通总结、Worket 确认后的定义”。尽量控制执行者、任务难度与预算，比较交付通过率、返工次数、人工解释与检查时间、总体费用，并保留反例。后续再更换执行者，单独验证迁移能力；避免同时更换模型与定义而混淆收益来源。候选生成、评审、执行和维护成本均计入。

人类确认和真实交付效果承担不同职责：前者确定目标、约束及可接受的取舍，后者检验方法的效用。效果评测不能自动改写业务约定或授权，原始 WorkRecord 也不因短期未提升指标而删除。该设想不改变现有用户主动沉淀的边界，不授权自动训练或扩大采集。

### BP 候选表达与展示场景

方向性表述：**Worket 希望把企业的工作经验变成可复用、可验证、可持续改进的工作资产，让每次沉淀都有后续交付证据。**

展示可选择一类报告：从首份报告的实际修订中确认定义，用不同输入完成后续报告，展示定义版本、返工变化和人工投入。只有取得真实对照证据后，才能表述为 Worket 已验证的优势。MemOp 支持的是评测思路，不能替代企业场景或 Worket 的效果验证。

## B003 — 从理解用户意图到提炼可复用的工作约定

### 讨论起因与用户观点

2026-09-10，用户询问本地运行或复现 ToM-SWE 的机器要求，并明确希望基于该研究，从用户实际对话中提炼 WorkDefinition。这是研究和算法探索方向，不代表批准新增数据采集、训练或改写产品流程。

### 已核实的研究事实

核实日期：2026-09-10。ToM-SWE 以原始会话、单会话用户分析、跨会话用户模型构成三层记忆，为软件工程执行 Agent 提供目标、约束与偏好方面的建议。论文验证的是编码任务和用户建模，并未直接验证 Worket 所定义的可复用工作约定。来源：[论文 v2 第 2 节及附录 A.4](https://arxiv.org/html/2510.21903v2)、[官方代码](https://github.com/OpenHands/ToM-SWE)。

### 对 Worket 的洞察与当前依据

助手提出的洞察：真实对话中的纠正、否定、验收反馈，可能比孤立的初始指令更能表达工作的真实要求。把这些信息转成可追溯的候选约定，有机会降低用户事先编写工作定义的负担。用户的一般交流偏好、本次工作的例外、同类工作的稳定要求须分别判断；反复出现并不自动成为通用规则。

当前依据：[领域定义](../../CONTEXT.md) 已将 WorkDefinition 与 WorkRecord 区分；[现有提炼流程](../../server/workflow.mjs) 已实现分块提取、纠正关系整合、跨工作泛化和来源校验。当前中间结构保留文本、范围、来源和替代关系，但用户陈述/Agent 提案、确认状态等信息尚未逐项成为独立的中间字段。这提供了一个可实验的改进点，不能据此断言现有真实样本效果已被证明不足。

### 助手提出的设计设想与验证

保留现有工作定义契约，实验性增强“对话证据 → 单次工作要求 → 同类工作共性与变量 → 候选定义”流程。将发言来源、纠正与撤销、适用范围和证据回查显式化；对不确定的泛化提出问题，参考方法默认不升级为强制步骤。最终仍由用户主动沉淀并确认。

在同一模型和相近预算下比较直接提炼、现有两阶段流程、上述增强流程；先评估关键要求遗漏、错误泛化、来源错误和用户修订量，再用未参与开发的同类记录及新输入检验复用。一个小样本只能用于发现问题，不能支持整体效果宣传。

### 用户价值与可展示场景

潜在价值：让用户在正常工作与纠正 AI 的过程中逐渐形成可复用约定，减少重复解释。以客户报告为例，保留“指标必须可追溯”等稳定要求，将客户、日期和数据改为本次输入，并识别“这次先不做竞品分析”为本次例外。展示每个候选条目的对话依据，以及下一次工作的交付效果。

BP 候选表达（方向性）：**Worket 希望把用户在真实协作中表达和修正的要求，转成可确认、可复用、可验证的工作定义。** 其准确率、节省时间和跨执行者收益仍待真实实验；研究笔记见 [ToM-SWE 可行性分析](../research/tom-swe-feasibility.md)。
