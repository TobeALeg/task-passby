# Worket 交接成本与有效性评估方法 v0.1

状态：研究设计，尚未批准为产品功能或完成真实实验。
日期：2026-09-12

## 1. 要回答的问题

在来源记录、目标任务、接收执行者、工具权限和预算相同的条件下，一种交接方法是否能：

1. 让目标执行者正确延续同一项工作；
2. 减少用户重复说明、目标执行者读取上下文和返工的成本；
3. 不把过期决定、无关历史或未经证实的内容错误带入后续执行。

评估单位不是一段摘要，而是一次完整的**交接回合**：从来源工作在确定时点形成快照，到一个全新的目标会话接手并产出可验收结果。

这里评估的是同一 WorkInstance 的交接，不是从历史工作抽象 WorkDefinition 的“沉淀”。两者应分开实验。

## 2. 当前实现与实验基线

当前实现已经不只是传递原始聊天和文件路径：`HandoffPackage` 包含八部分结构化 Work State、当前任务、下一步、最新资料引用和来源档案数量；目标执行者先通过 `get_work_context` 读取交接快照，需要核验时再调用 `get_work_archive`，资料引用可通过 `get_artifact_refs` 获取。完整来源档案不默认进入主 Prompt。

因此至少比较以下条件：

| 条件 | 交给目标执行者的内容 | 用途 |
| --- | --- | --- |
| C0 无交接 | 只有“继续这项工作”的任务指令 | 测量下限，不作为产品方案 |
| C1 原始直传 | 截止时点的完整可见聊天记录和全部资料引用 | 对应“简单搬运”基线 |
| C2 当前 Worket | 当前 Handoff Package；来源档案与资料按需读取 | 测量现状 |
| C3 候选整理 | 待测试的新组织方法，例如去重、标记已失效决定、区分必须知道与按需核验信息 | 测量改进增量 |
| C4 人工理想包 | 熟悉工作的人手工整理的最小充分交接包 | 只在部分样本使用，估计上限 |

C1、C2、C3 必须从完全相同的来源快照生成。不能让某一条件看到更多消息、更新的文件或额外提示。

## 3. 每个案例先建立“交接契约”

在生成和查看各条件的交接包之前，由工作发起人依据来源记录确认一份小型金标准。每条信息保存来源证据、重要度和交接策略：

- `MUST`：目标执行者开始后必须掌握，例如当前目标、不可违反的约束、已确认决定、已经完成的动作、下一步和必需资料；
- `ON_DEMAND`：不必预先塞入主上下文，但目标执行者遇到对应问题时应能找到；
- `MUST_NOT_ACTIVATE`：存在于历史中，但已被撤销、替代、否定或仅是探索方案，不得当作当前事实执行；
- `NEW_DECISION_REQUIRED`：来源中没有答案，目标执行者应该向用户询问，不能猜测。

重要度建议为关键 `5`、重要 `2`、辅助 `1`。关键项遗漏或错误不能被大量低价值信息的正确覆盖抵消。

交接契约还应包含：

- 截止时点与来源事件范围；
- 目标执行者接手后的具体任务；
- 允许使用的工具和资料；
- 可自动检查或由真人盲审的交付验收标准；
- 哪些提问属于合理的新决策，哪些属于本可避免的重复说明。

## 4. 成本口径

不把所有成本过早合成一个分数，至少分别报告用户成本、机器成本和经过时间。

### 4.1 准备成本 `C_prepare`

- 整理交接包的模型输入/输出 token、调用次数和费用；
- 从点击交接到包可用的延迟；
- 用户检查、修正或确认交接包的时间与操作次数。

### 4.2 传输与理解成本 `C_ingest`

- 首次注入目标会话的 token/字节数；
- `get_work_context`、`get_work_archive`、`get_artifact_refs` 等读取次数、返回 token 与延迟；
- 实际打开的资料数量和读取量；
- 从目标会话启动到首次**有来源依据的有效动作**所需时间。

### 4.3 恢复与返工成本 `C_repair`

- 用户重新说明来源中已有信息的次数、token 和用时；
- 由误解引起的澄清轮次、纠正轮次、撤销动作与重做量；
- 从第一版交付到通过验收的额外模型费用、工具调用和经过时间。

最终报告以下三个总量，而不是只报“包有多短”：

```text
C_user    = 准备确认时间 + 重复说明时间 + 检查和纠正时间
C_machine = 整理费用 + 目标执行输入/输出费用 + 工具和返工费用
C_elapsed = 点击交接到最终通过验收的墙钟时间
```

上下文 token 少但导致大量追问和返工，不算低成本；反之，包更长但显著减少人工干预，也可能更便宜。

## 5. 有效性口径

### 5.1 主结果

1. **首版通过率**：第一次可验收交付是否满足全部关键标准；
2. **最终通过率**：在固定预算内能否通过；
3. **关键错误率**：是否遗漏或违反重要度为 5 的目标、约束、决定或资料要求；
4. **用户分钟/通过案例**：达到通过所需的用户总投入。

一次“严格有效交接”定义为：固定预算内通过验收、没有关键错误，并且没有要求用户重新解释来源中已经存在且应属 `MUST` 的信息。目标执行者对 `NEW_DECISION_REQUIRED` 发问是正确行为，不计为失败。

### 5.2 诊断指标

- **加权必需信息召回率**：正确理解的 `MUST` 项权重之和 / 全部 `MUST` 项权重之和；
- **错误激活率**：被当作当前事实使用的 `MUST_NOT_ACTIVATE` 项 / 全部此类项；
- **连续性**：是否从正确下一步开始，是否重复已完成动作，是否保持同一 WorkInstance 的目标；
- **资料落地率**：需要时是否选择正确文件、版本与用途，结论能否回到对应来源；
- **按需检索质量**：该查档案时能否查到，不需要时是否避免无差别读取全部历史；
- **无依据新增**：目标执行者是否把交接包和来源中都没有的内容当作已确认事实。

状态理解测试和真实执行应使用两个独立的新会话：前者要求目标执行者回答交接契约问题，用于诊断；后者直接完成任务，避免“考试问题”反过来提示执行者应该关注什么。

## 6. 实验流程

1. 选取 8–12 个真实 WorkInstance 做探索性试验，覆盖长短对话、不同资料数量、开发与非开发任务，以及 Codex → WorkBuddy、WorkBuddy → Codex 两个方向。
2. 在自然的接力点冻结来源快照，工作发起人先确认交接契约；不根据候选包反向修改金标准。
3. 从同一快照生成 C1、C2、C3；在部分案例增加 C0、C4。
4. 每次运行都创建全新目标会话，固定目标 Agent/模型版本、系统指令、工具权限、预算和任务截止条件。条件名称对目标执行者隐藏。
5. 随机化条件顺序；每个“案例 × 条件”至少独立运行 2 次，正式比较建议 3 次，以观察 Agent 随机性。
6. 代码任务优先使用测试、静态检查和产物差异验收；文档或分析任务由不知道条件的真人按预先确定的量表审阅。模型评分只能作辅助诊断，不能独立判定产品收益。
7. 记录完整的准备、读取、执行、追问、纠正和验收事件。失败案例保留，不因“模型发挥异常”事后删除。
8. 按案例做配对比较，并按交接方向、任务类型、来源长度、资料数量分层报告；同一案例的重复运行不能当作彼此独立的真实工作数量。

探索阶段 8–12 个案例、三种主要条件、每种两次，共 48–72 次运行，只用于发现效应和失败模式。形成产品结论前应扩大真实案例，并报告配对差异和置信区间。

## 7. 决策规则

先过安全门槛，再看成本—效果前沿，不用一个容易掩盖问题的总分排序。

候选方法 C3 进入下一阶段的建议门槛：

- 关键错误率不高于 C2；
- 最终通过率不低于 C2，探索期允许的非劣界值暂定为 5 个百分点；
- 并且满足以下至少一项：用户总时间下降 20%，总目标端输入 token 下降 20%，或首版通过率提高 10 个百分点；
- 优势不能只来自让 C3 使用更多工具、更多预算或更新的模型。

这些数字是试验启动阈值，不是已验证的产品承诺。若 C3 提高效果也提高成本，应报告“每多获得一个严格有效交接所增加的成本”，由具体场景决定是否值得，不强行折成统一效率分。

## 8. 最小埋点

每次运行至少记录：

- `handoff_id`、`work_id`、来源截止序号、交接方法与版本；
- 来源/目标执行者、模型与版本、工具权限、预算；
- 包生成起止时间、模型调用量、用户确认时间；
- 初始包 token、各 MCP 读取的工具名、时间、返回 token 和来源范围；
- 首次有效动作、首版交付、每次用户澄清/纠正、最终验收的时间；
- 交接契约逐项判定、资料使用、测试结果和失败原因。

当前 `HandoffPackage` 快照、`packageReadAt` 与 MCP 工具读取审计可提供部分基础证据；正式实验仍需补齐交接方法版本、准确 token/费用、`get_work_archive` 读取范围、用户投入时间和逐项验收结果。

## 9. 首轮产出

首轮不以“平均摘要分”作为结论，应交付：

1. 各条件的首版/最终通过率、关键错误率和三类成本；
2. 每个案例的配对结果与失败链路；
3. 哪些信息应主动进入主上下文、哪些适合按需检索、哪些必须标记失效；
4. C2 当前方案最昂贵的环节，以及 C3 是否真的减少了总成本；
5. 可复现的来源快照、交接契约、方法版本和验收记录。

只有“目标执行者完成真实后续工作”能证明交接有效；包更短、结构更漂亮或目标执行者能复述背景，只能作为解释结果的中间证据。

## 10. 本机数据就绪度与分阶段启动

2026-09-12 对当前 Windows 本机做了只读、仅聚合元数据的盘点，没有输出会话标题、正文或工作路径：

- Codex 发现 5 份会话文件，总计约 17.23 MB；
- 其中 1 份较长，包含 18 个执行轮次、19 条用户消息、48 条助手消息、150 个工具事件和 13 个图片输入；
- 其余 4 份分别只有 1、1、3、3 个执行轮次；
- 本机 `.workbuddy` 目录只发现运行时、命令与日志类文件，没有发现可直接用于本轮评测的 WorkBuddy 会话存储；当前也没有本机 `.workpet` 数据目录。

因此，当前数据足以开展一次“单案例 × C1/C2/C3 × 各 2–3 次”的流程走通和失败模式诊断，但不足以支持 8–12 个独立真实 WorkInstance 的探索性结论，也不足以比较两个交接方向。可以在长会话内选择多个自然截止点调试评测工具，但统计时仍只能视为同一工作的相关观察。

建议分三步积累：

1. 先用唯一长案例完成埋点、交接契约和盲审流程，不对外声称收益；
2. 之后由用户主动选择 5–10 个自然发生、确实准备换 Agent 的工作，在交接前冻结快照；不为凑样本自动采集其他聊天；
3. 达到至少 8 个独立工作且两个方向都有覆盖后，再执行本方法第 6 节的探索性比较。

合成样本可以覆盖罕见的撤销决定、文件版本错误和长历史等边界情况，但只能验证评测与工程机制，不能替代真实用户成本和交付效果。

## 11. 公开数据的补充方案

核实日期：2026-09-12。公开数据的数量足以建立交接机制基准，但不同数据只能覆盖证明链的一部分：

| 数据 | 已核实规模与许可 | 适合验证 | 不能证明 |
| --- | --- | --- | --- |
| [SWE-smith Trajectories](https://huggingface.co/datasets/SWE-bench/SWE-smith-trajectories) | 数据卡描述 5,017 条由 SWE-agent 与 Claude 3.7 Sonnet 生成的轨迹，带任务实例、消息、是否解决和补丁；MIT | 在可重建代码仓库中从中途状态换执行者，比较测试通过、重复探索、token 与返工 | 不包含真实用户在多轮中修改要求；轨迹是模型生成，且公开任务可能被目标模型见过 |
| [ThoughtWorks Agentic Coding Trajectories](https://huggingface.co/datasets/thoughtworks/agentic-coding-trajectories) | 15,000 个会话、618K turns、3–120 turns，约 326 MB；派生数据，逐行受上游许可约束 | 快速按长度、框架与成败筛选编码交接前缀 | 没有现场工具环境；不能不检查上游许可就整体作为统一许可数据使用 |
| [WebLINX](https://mcgill-nlp.github.io/weblinx/) | 2,300 个专家演示、约 100K 次交互、150 多个网站，含多轮对话、HTML、截图和动作；CC BY-NC-SA 4.0 | 测试指令变化、网页状态与下一动作交接；可通过官方 BrowserGym 形式读取演示步骤 | 非商业许可限制明显；网站状态未必能原样重放，也不是 Codex/WorkBuddy 工作 |
| [WildChat-4.8M](https://huggingface.co/datasets/allenai/WildChat-4.8M) | 当前公开非有害内容版本为 3,199,860 份真实用户—ChatGPT 对话；ODC-BY。“4.8M”指完整原始版本规模，清洗版已过滤毒性内容并移除已验证密钥 | 筛选长对话，测试目标变化、纠正、否定、话题延续和结构化提取的忠实度 | 没有文件、工具环境、Agent 切换和客观交付结果，不能评估真实接手后的完成率或用户返工时间；仍需额外敏感信息筛查 |

建议采用三层样本，而不是把所有公开聊天混成一个分数：

1. **可执行交接集**：从 SWE-smith 选 30–50 个可重建、测试稳定、许可证清楚的任务。在自然中途点保存仓库状态，只向 Worket 暴露用户可见消息、工具调用/结果和文件事实，排除轨迹中的隐藏推理；让新执行者从同一状态继续到测试验收。
2. **多轮状态交接集**：从 WebLINX 选 30–50 个至少包含一次用户补充或状态变化的演示，测交接后下一动作、关键约束和无效旧指令激活。先作为非商业研究资产，不混入可自由商用的数据包。
3. **自然语言压力集**：从 WildChat-4.8M 筛选 50–100 份足够长、去标识且无明显敏感内容的对话，在中间插入模拟交接点，用真实后续用户消息检查新执行者是否延续前文目标、约束与修正；抽取其中 20 份人工复核。它只能测上下文表示和继续回应，不能计入真实交付通过率或用户成本。

公开数据的选择、过滤规则和截止点必须预先保存成 manifest，保留数据版本、来源 URL、许可、哈希和排除原因。目标模型可能见过公开任务，因此应使用同一模型做条件内配对比较，并单列 C0 无交接条件；若 C0 也能完成，不能把该案例当作交接方法带来的收益证据。

这三层公开数据足以开发评测工具、发现失败模式并比较 C1/C2/C3 的机制差异；要支持 Worket 的产品价值表述，仍需用户授权的真实自然交接，测量重复说明时间、主观负担和最终验收。

WildChat 的跨模型接收者校准、交接点、实验条件、效应量和评分流程另见 [WildChat 跨模型交接评测方案 v1](wildchat-handoff-evaluation-v1.md)。

WildChat 使用时不应保留或利用国家、州、哈希 IP 和请求头；优先排除 `redacted=true`、空用户输入、明显敏感内容和无法判断是否属于同一项工作的对话。只在本地保存上游 ID、筛选标签和评测分数，不把聊天正文提交到仓库。公开非有害版本约 15.3 GB 下载、解压后约 42.6 GB，无需为首轮实验完整下载；应先按数据版本与分片做流式筛选，再冻结入选样本 manifest。
