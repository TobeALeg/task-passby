# 如何定义一项高质量任务

**Worket 值得研究的核心能力，是以较低的沟通成本，把人的零散表达、相关背景和未确定之处，形成足以开展工作的共同约定。** 清晰的 Prompt 是一种输出形式；真正需要验证的是，这份约定是否保留了人的意图、处理了重要分歧，并让实际交付更容易被接受。

“帮用户说出未说出的话”准确抓住了其中一部分价值，但包含不同问题：找回已经说过的内容、解释当前隐喻、推断隐含偏好、发现冲突，以及帮助形成尚不存在的决定。它们需要不同证据，也需要不同交互。把这些全部交给一次自动补全，容易得到清晰却失真的任务。

Abstract 与 Memory 也不是互斥能力。现代 Memory 已经会归纳经验与偏好，部分产品还提取承诺和约束。Worket 的潜在价值需要落在更具体的环节：**哪些理解适用于这项工作，怎样低成本形成可靠约定，以及这份约定能否经受执行、修订和复用。** 这是一项待验证的产品命题。

## 1. 研究结论及其强度

| 判断 | 证据强度与边界 | 对 Worket 的意义 |
|---|---|---|
| 任务定义已有独立研究和产品先例 | IN3 直接研究上游意图理解；[Spec Kit](https://github.com/github/spec-kit)、[Kiro](https://kiro.dev/docs/specs/analyze-requirements/) 已提供规格与澄清流程 | 竞争定位不能建立在“别人都只解决任务”上 |
| 一些目标和偏好会在互动中形成 | 设计研究、偏好构造理论与 EvalGen 提供不同范围的支持 | 保留探索、示例比较和修订，不假设完整答案总藏在用户脑中 |
| 选择性澄清可以改善部分下游任务 | 公开受控实验支持，但大量实验采用模拟用户及预设完整需求 | 用真人工作检验收益，单独计算沟通成本 |
| Memory 已能承担一部分 Abstract | A-MEM、Mem0 Dream、Zep Observations 有直接方法或官方能力说明 | 比较工作流程和效力边界，不能只比较“是否做抽象” |
| 结构正确、理解正确、许可有效、交付可用是不同要求 | 需求工程、权限研究及 Agent 评测提供互补依据 | 评测不能只看 JSON、文字完整度或最终工具调用成功 |
| Worket 现有模型提供了部分基础 | 当前领域文档、定义契约和沉淀规格有来源、草稿、版本、验收等机制 | 优先研究真实案例中的缺口；跨执行者身份本身不证明用户收益 |

以上结论分别展开于下文及四份专题：[人类问题形成](human-problem-formulation.md)、[LLM 澄清实证](llm-clarification-evidence.md)、[产品与协议现状](product-and-protocol-landscape.md)、[Abstract 与 Memory](memory-and-abstraction.md)。专题保存论文设置、准确版本、原始链接和限制，便于后续复查。

**后续补充：同类工作反复执行。** 已有 AgentMemoryBench 等基准在顺序执行新任务时持续更新记忆，也有 MemoryArena 将记忆用于跨会话行动。因此，不能把 Memory 评测全部概括为对话问答。用户提出的“同一用户、一类工作、五个独立实例、逐次交付与反馈”需要进一步区分在线经验迁移、一次大任务续做和同题重复测试；具体证据及研究方案见 [重复工作序列评测](repeated-work-evaluation.md)。

## 2. 一项任务到底是什么

本文采用一个用于产品研究的定义：**任务是在具体情境下，为某个主体达成一种结果或取得足以支持下一步的认识，在一定行动边界内开展，并有办法判断进展或完成的一项工作。** 它不要求结果一定是文件，也不要求执行方法预先固定。

几个概念需要分开：

| 概念 | 所回答的问题 | 构造示例 |
|---|---|---|
| 动机 / 意图 | 为什么关心这件事？ | 担心客户看不懂公司的价值 |
| 问题定义 | 现状与想要的状态之间，具体缺口是什么？ | 官网能介绍功能，但访客难以判断适用场景与可信度 |
| 工作约定 / 任务规格 | 本次要改变什么，满足哪些条件？ | 给出并验证一版首屏及关键内容结构，支持访客做下一步判断 |
| Prompt | 用什么表达把信息交给某个系统？ | 一段指令，附来源、约定与当前输入 |
| 计划 | 准备怎样达到约定？ | 查材料、形成信息层级、出稿、检查、修改 |
| 当前状态 | 到现在发生了什么，什么还有效？ | 已确认目标读者，布局仍待比较 |

同一份工作约定可以用不同 Prompt 交给不同执行者；同一目标也允许不同计划。这种分离可以减少执行器切换时的语义损失，但“任意执行者都能完成”仍取决于能力、环境、材料和权限。

任务粒度也应以工作判断为中心。一个会话可以有多个任务；同一任务可以跨多个会话。可先用三个问题判断是否值得单独成项：能否独立表达预期结果；能否独立验收或决定下一步；能否在不丢失关键依赖的情况下交给另一执行者。它们是启发式原则，不是自动切分的已验证算法。

对于探索任务，验收可以是“明确几种有证据支持的解释、指出仍缺什么、提出下一项判别实验”。不必在研究开始前假装已经知道结论。对于执行任务，则需要更明确的输入、输出和完成条件。

## 3. 人类协作提供的基础

NASA 的需求定义方法同时检查表述、技术正确性、利益相关方需要、可行性、可验证性，以及是否重复或过度规定；也要求保存理由与假设。这里最值得借用的是这些检查之间的区别。日常任务未必需要航天工程的正式流程，但文字规范并不能代替对实际需要的验证。[^1]

Dorst 与 Cross 的设计过程研究表明，问题和方案可能共同演化；Slovic 对偏好构造的分析提醒，复杂选择中的回答也会受到呈现程序影响。由此提出的产品判断是：任务定义应允许合理变化，同时不能把所有变化都称为“挖出了真正意图”。有些变化来自学习，有些可能来自模型的引导。[^2][^3]

Clark 与 Brennan 的 grounding 框架关注当前协作目的所需的共同理解和总沟通成本。对 Worket 的启发是，可以通过相关回应、简短复述和可检查的小样建立理解证据；它不支持逐句审批，也不能保证模型拥有与人相同的默契。[^4]

隐喻应被当作线索保留。专业设计讨论研究发现，类比承担解释、方案生成等不同作用；因此“像一个编辑部”可能在说筛选、层级、节奏或责任分工。具体指哪一项，需要情境支持，不能直接翻成报纸纹理和衬线字体。后半部分是设计推论。[^5]

近期 HCI 研究进一步表明，可检查的解释和例子值得研究，但不能夸大效果。“What It Wants Me To Say”的 24 人研究没有发现时间等量化指标的显著优势；EvalGen 观察到评价标准随着看过输出而变化。它们支持研究“展示理解”和“共同形成标准”，尚不能证明某一种界面普遍提高效率。[^6][^7]

## 4. LLM 研究已经验证到哪一步

最接近本课题的先例是 IN3 / Mistral-Interact：判断任务是否含混、定位缺失信息、提问，再把目标交给下游 Agent。其研究包含真人交互，但下游 XAgent 概念验证只有 10 个任务。它证明这个问题可以独立建模和实验，不足以给 Worket 提供普遍收益预测。[^8]

| 研究方向 | 主要发现 | 不应外推的结论 |
|---|---|---|
| 歧义识别：CLAMBER | 识别是否含混本身可能失败，需要单独评估 | 旧模型的准确率就是当前产品表现 |
| 何时提问：Clarify When Necessary | 值得问的是有望改变错误结果的澄清，不是所有语义歧义 | 存在不确定性就应该中断用户 |
| 多轮整合：Lost in Conversation | 相当的信息分多轮呈现，可能受提前假设和旧回答影响 | 所有多轮对话都比单轮差 |
| 训练提问：AskBench | 补齐信息与回答准确率可提高，同时可能增加不必要提问 | 提问能力增强等于总体验改善 |
| 面向行动：SAGE / ClarifyBench | 围绕会改变工具参数的差异提问，有机会减少问题数 | 参数匹配就是最终业务成功或有效许可 |
| 可回答性：CLARITI | 问题相关、用户能答、不重复，需要一起优化 | 用户应该替 Agent 解决实现问题 |
| 真人迁移：用户模拟器研究 | 在某个模拟器中提升，未必能迁移至真人互动 | 模拟对话的高分足以证明真实产品价值 |

上述方向的实验设置、基线和引文见 [LLM 实证笔记](llm-clarification-evidence.md)。这里选两个容易影响决策的结果进一步说明。

Lost in Conversation 在受控碎片化任务中报告跨任务平均 **39% 的相对表现下降**，不是下降 39 个百分点。最终信息量相当，仍可能因为之前的错误假设而失败。这提示“检索到背景”之后还需要维护当前有效要求，而不是把新旧话语不断堆在一起；后一句是待验证的设计假设。[^9]

CLARITI 在 250 个被删减需求的软件任务中，固定下游执行器，无澄清成功率为 **22.4%**，其训练后的澄清模块为 **36.8%**，完整 issue 条件为 **41.6%**。这说明上游缺口有可能成为重要瓶颈；但“用户能否回答”由完整 issue 中是否包含答案代理，没有真人参与该项验证，也不能推广为所有知识工作的提升。[^10]

大量基准先预设一个完整意图，再删除信息让模型问回来。它们适合研究遗漏恢复，却弱化了现实里的目标形成、隐喻解释、反悔、多个利益相关方和有限耐心。这应成为 Worket 评测补充的重点，而不是只换一个更大的模型。

## 5. 从零散表达到工作约定，需要哪些操作

下面是一组待实验的操作职责，可以通过一个模型或多个阶段实现；没有证据要求立刻搭建复杂 Agent 系统。

| 操作 | 目的 | 典型检查 |
|---|---|---|
| 恢复 | 找回指代对象、历史规则和相关材料 | “按上次”到底指哪次，规则是否仍适用？ |
| 组织 | 把跨消息碎片归到当前目标、事实、要求和决定 | 这段是用户要求，还是助手曾提出的方案？ |
| 解释 | 提出隐喻、含混词语的候选含义 | 不同解释会不会改变交付或行动？ |
| 发现缺口 | 识别缺失事实、冲突、不可行条件和重要未知 | 是需要查资料、问用户，还是需要试验？ |
| 形成约定 | 把确定部分和有依据的选择组织起来 | 什么来自明确表达，什么仍是提案？ |
| 验证和修订 | 用样例、检查与真实工作发现偏差 | 新证据改变了要求，还是旧理解本来就错了？ |

任务定义系统尤其需要保留“事实”“偏好”“要求”“方法”“授权”的不同地位。“用户用过某工具”不是“必须用此工具”；“上次这种方法成功”也不直接成为长期必需步骤。目标导向需求工程对目标、环境假设和实现要求的区分提供了方法依据。[^11]

系统还应接受“目前无需处理”。有些歧义不改变下一步，有些可以低成本改回，有些正是探索空间。如果给每个空字段都生成问题，就会把用户本来交给 AI 的整理工作重新交还给用户。

## 6. 一个最小任务约定需要承载什么

**完整程度应由下一步决策决定。** 下表是检查视角，不是要求用户填写的表单，也不是新的数据库契约。

| 视角 | 最小有用内容 | 常见错误 |
|---|---|---|
| 目的与对象 | 为谁解决什么问题，支持什么结果或决定 | 把“写一份报告”当作完整目的 |
| 本次情境 | 相关事实、材料、时间、环境和依据 | 把全部聊天历史当作背景；遗漏来源与适用条件 |
| 交付 | 可检查的产物、状态变化或研究认识，以及必要形式 | 只规定输出 JSON，却不说明内容是否可用 |
| 质量与验收 | 谁来判断、看什么证据、允许哪些合格变体 | 把唯一范文、页数或模型自评分当成成功 |
| 约束与取舍 | 必须遵守的条件、预算、优先级、排除范围 | 给用户没有选过的实现细节加上“必须” |
| 行动范围 | 可读、可改、可对外产生何种效果，以及有效授权依据 | 参数齐全就执行；或已有授权仍逐次询问 |
| 开放问题与更新 | 什么仍未知，为什么影响下一步，何时回看 | 强行填满未知；修正后旧条件继续生效 |

每个重要条目还应可回答：依据在哪里；是用户当前陈述、历史约定、模型推断，还是新选择；适用于什么范围；是否已被替代。这些元信息首先服务于保真和修订，不要求全部展示成复杂界面。

停止定义的条件可以是：接下来要做的事已清楚，关键结果与边界不存在会造成实质分歧的缺口，余下未知有处理方式。所谓“准备好”不是没有未知，而是未知不再妨碍当前这一步可靠开展。这是产品启发式判断，需要用真实任务校准。

## 7. 什么时候问，什么时候读材料，什么时候先做小样

建议把一次澄清的价值理解为：**它有望减少多少错误与返工，是否足以抵消回答、等待、审阅及引导偏差的成本。** 这不是目前能精确计算的通用公式，更不能用模型自报的置信度冒充真实概率。

| 缺口 | 优先研究的动作 | 原因 |
|---|---|---|
| 答案在已授权材料里 | 查找并给出依据 | 避免要求用户重复提供已有信息 |
| 有清楚、适用的持续性偏好 | 采用并允许纠正 | 让记忆减少沟通负担 |
| 不同回答会改变目标、关键交付或行动范围 | 提一个具体问题，说明影响 | 解决真正改变工作的差异 |
| 用户难以描述审美或“哪里不对” | 给少量有差异的小样，固定无关变量 | 帮助形成可观察的选择 |
| 低影响、可逆且有合理默认 | 带着可纠正的假设继续 | 避免把常规判断外包回用户 |
| 新结果显示原定义不可行 | 解释冲突，提出调整 | 保留用户决定目标与取舍的地位 |

例如“做一个像成熟公司的网站”，先弄清访客与商业目的，可能比询问色号重要；但若访客和目的已在现有材料中明确，重复询问同样是失败。问题要针对当前缺口，而不是根据任务类别机械生成。

在开放任务里，小样既是产物也是探测工具，但有两个限制：它可能锚定用户；多个维度同时变化会让选择难以解释。应记录选择涉及的具体内容，允许自填、局部修正、拒绝所有候选和保留开放性。IntentTagger 为微粒度意图控制提供交互先例，但其短期小样本研究不能决定 Worket 的最终界面。[^12]

## 8. Abstract 与 Memory：真正的重叠和区别

从能力定义看，Memory 负责跨时间延续信息和经验，Abstract 是从具体表达与证据形成更有用表示的操作。一个 Memory 系统可以包含 Abstract，一个任务定义过程也可以生成 Memory；已确认的 WorkDefinition 可以是组织记忆的一种。

目前已有很具体的重叠：Mem0 Dream 能归纳高阶模式；Zep Observations 还会汇总决策、承诺、约束和偏好。因而不能把“输出里出现要求或承诺”本身当作 Worket 的独有区别。[^13][^14]

建议以三层关系理解产品职责：

| 层次 | 需要回答的问题 | 例子 |
|---|---|---|
| 证据与历史 | 过去发生或表达过什么？ | 上次报告因赶时间做了五页 |
| 解释与适用性 | 它支持什么理解，现在是否成立？ | 五页是临时妥协，未必是长期偏好 |
| 工作约定 | 这一次或这类工作采用什么要求，如何检查？ | 本次面向五分钟评审，交付一页决策摘要与证据附件 |

这三层都可以被保存进 Memory；关键是系统怎样区分它们，并处理从一层到另一层的依据。历史事实没有自动的规范效力，但历史里已有明确且有效的长期要求或授权，可以在适用范围内继续生效。

对 Worket 来说，值得验证的增量是：以 Work 为单位组织这些关系，降低采用和修正成本，并把交付反馈接回来。来源追溯、版本化和跨 Agent 都已有相邻实现，单独列为功能并不构成差异化证明。

详细技术例子、8 项论文与官方依据、权限记忆规则，以及区分 Memory / Abstract 增量的 2×2 实验，见 [专题报告](memory-and-abstraction.md)。

## 9. 为什么权限和验收要独立看待

“明确用户需要什么”与“确定允许系统做什么”相互关联，但不能混成一个字段。阅读授权材料、形成草稿、修改业务系统、发给外部对象，可能有不同有效范围。用户确认内容，也不必然授权外发；反过来，明确的既有授权不应因进入新对话就被无故丢失。

MCP 当前版本提供 elicitation 的输入交互，A2A 提供等待输入和等待授权的状态；它们解决部分协议与控制问题，不会自动验证整项业务的意图和完成标准。本报告采用 MCP 2026-07-28 与 A2A 1.0.0 的固定版本；A2A 动态 latest 的新增条款另在专题中标明，避免混用。[^15][^16]

验收也不能只追一个方便测量的代理目标。Specification gaming 说明系统可能满足文字上的指标而错过想要的结果；把“有十个引用”设成标准，不等于十个来源确实支持关键判断。任务验收应检查结果，也检查有明确要求的过程义务。[^17]

对探索型和创造型工作，应允许不同合格成果。标准因新证据而调整时，要保留理由和变化时间，避免看到失败产物后降低标准，再把它记为成功。Anthropic 的 Agent 评测实践也强调回看轨迹，区分真实失败、错误评分和被拒绝的有效解法。[^18]

## 10. 对 Worket 当前方向的映射

当前 [CONTEXT](../../../CONTEXT.md) 把 WorkDefinition、WorkInstance、WorkRecord 与执行者分开；[定义契约](../../../src/contracts/definition.ts) 已有目的、输入、交付、约束、验收、方法、资料与依据；[沉淀规格](../../specs/work-distillation-v1.md) 保留用户主动触发、候选审阅和固定版本。这些可直接支持研究，暂时没有证据要求扩张所有数据结构。

新的研究重点与现有沉淀路径有两种联系：

| 路径 | Abstract 的主要工作 | 应检验的价值 |
|---|---|---|
| 从已经发生的工作中沉淀 | 识别稳定要求、本次变量、例外与参考方法，形成可复用候选 | 下一次同类工作是否减少重复说明和返工？ |
| 在正在形成的工作中澄清 | 组织碎片、恢复背景、解释隐喻、帮助形成目的与验收 | 首次交付是否更符合需求，且没有增加过多前置负担？ |

两条路径可以共用证据处理与抽象能力，但不等价。已经做过的工作有纠正、结果和反馈；新工作可能只有愿望与材料。将后一种能力用于产品，需要另行确定入口和验收，不能把它当作现有沉淀效果已经证明的自然延伸。

有一个可优先验证的承接方式：先从已有工作中提取候选，下一次复用时观察哪些条件必须重新讨论。这样既检验 Memory 的帮助，也能发现 Abstract 是否真正减少描述成本，符合现有“记录—沉淀—新实例”的路径。它是较低准备成本的研究路线，不排除后续单独研究从零开始的意图形成。

## 11. 推荐的研究实验

### 先建立可诊断的案例

先收集约 10–20 个经授权的真实案例用于发现错误，覆盖三类工作：材料研究与决策、业务文档制作、现有产品的定向修改。这个数量只用于诊断与试验流程，不代表足以推断总体效果；正式研究需要根据观察到的方差、目标效应和用户相关性确定样本量。

每例保留最初自然表达、当时可见资料、后续修正、有效许可、最终产物与验收依据。对已经完成的案例，事后答案只供评审，不能提前给参与比较的系统。用户负责裁定关键业务歧义，不应被要求先写一份完美规格。

同时标记几类重要反例：明确且无需多问；背景可从记忆找回；隐喻存在多解；当前要求覆盖旧偏好；存在冲突或不可行条件；目标仍在形成。只有成功案例的集合不能检验系统何时应该停止提问。

### 区分各部分到底贡献了什么

核心对照是原始执行、只加 Memory、只加 Abstract、两者组合。另加一次性整理文本的基线，区分“把已有信息组织好”和“获得新信息”的效果。这里“无 Abstract”仅指没有本研究的显式工作约定流程；Memory 原有的归纳、规则学习和强模型的自然澄清能力都应保留，不能故意限制它们来制造优势。

固定执行器、材料、环境及评价口径；记录交互额度和实际消耗。可以再把同一份已形成约定交给不同执行器，检查可迁移性，但执行器不同不能混进第一轮因果比较。

| 维度 | 第一轮记录 | 后续可量化指标 |
|---|---|---|
| 意图保真 | 必须保留、不能继承、允许变体、证据不足 | 关键要求遗漏、无依据新增、错误范围继承 |
| 用户成本 | 说明、回答、审阅、修正和返工时间 | 总主动投入时间、无效提问、退出率 |
| 交付 | 按当次约定逐项检查，允许未验证 | 首次可接受交付、实质返工、合格率 |
| 授权与过程 | 对照有效范围和操作轨迹 | 越界尝试、遗漏已授权动作、重复申请 |
| 可修订性 | 记录新事实、纠正、改主意的区别 | 旧约束残留、已确认内容遗失 |
| 复用 | 记录新实例输入与例外 | 后续描述成本、维护成本、适用失败 |

应当分别保存“模型原始候选质量”和“人工修正后质量”。人工修好能够得到有用任务，但修正成本属于系统成本，不能被记为自动抽象成功。

### 检验几条能够被推翻的假设

1. **关键问题优于固定问卷。** 若交付质量相当而总用户成本没有下降，就没有得到支持。
2. **带来源与暂定状态的约定优于普通改写。** 若只是让文本更长，没有减少误读或修正，应该简化。
3. **Memory 能减少重复说明，但需要本次适用性判断。** 用过时偏好、例外及当前覆盖指令检查组合收益和污染。
4. **小样更适合部分难以言说的偏好。** 观察是否减少后续反悔，并检查是否只是把用户锚定在系统建议上。
5. **已确认定义能够复用。** 如果新实例仍需大量解释和维护，便不能把“成功保存模板”当成收益。

真人与模拟实验应分开报告。2026 年的用户模拟器研究发现，不同模拟器训练所得提升面对真人并不一致；自动评测适合扩大覆盖，仍需要实际用户检验其排序和负担。[^19]

现有 [WorkDefinition 提取执行依据](../../work-object-extraction-execution-plan.md) 已有同类记录、留出实例、原始候选与人工修订分开评分的原则。新的研究可以复用这套约束，增加开工前意图形成与 Memory 对照，避免另起一套互不衔接的评估。

## 12. 仍需要讨论的产品问题

最先要决定的是主要入口：帮助当前工作形成约定，还是从过去工作形成复用定义。两者都属于本研究，但用户期望、证据条件、确认方式和首次价值出现的时机不同。

第二个问题是用户看到什么。可以研究一份短而可修正的工作理解、可直接改动的候选、少量有差异的小样，以及只在重要缺口处出现的问题。现有文献不足以确定哪种界面最佳，也不支持先让用户填完一张通用任务表。

第三个问题是工作约定带来的独立价值。如果加上现成 Memory 和一个强模型就能获得相同结果，Worket 需要进一步证明工作范围、证据追踪、用户修订和跨次复用能降低成本。文献和产品对照目前不能替代这个实验。

另一个值得长期保留的判断是：完整规格并不总是经济或可能的。不完全契约研究讨论了认知成本与未来重新协商；Inverse Reward Design 把给定目标视为与设计情境有关的意图证据。对 Worket 的启发是保留适用范围和修订能力，不能据此授权系统用自己的猜测取代用户明确目标。[^20][^21]

**建议把下一阶段核心问题表述为：系统怎样判断“哪些未说出的内容可以可靠补出，哪些需要共同形成”，并以最小必要互动，使结果成为真实工作中可用的约定？** 这比统计 Prompt 字段数，更接近需要证明的产品价值。

## 证据范围

范围截止 2026-09-10，包含经典认知与需求工程文献、2023–2026 年 LLM/Agent 研究，以及访问时的第一方产品和协议文档。专题中区分理论、观察性研究、小型交互实验、模拟基准、预印本与官方功能声明；只读摘要的扩展线索另作标记。这里是多领域范围研究，未采用穷尽式系统综述流程。

公开研究多数没有覆盖中文高语境表达、长期真实工作、多个利益相关方、隐喻与动态目标的联合情境。产品比较基于文档，不能视为实测或采购结论；本地代码与规格的核对也不能代替业务验收。本文提出的交互、指标与产品职责均为研究建议，未将其写成已经生效的产品承诺。
