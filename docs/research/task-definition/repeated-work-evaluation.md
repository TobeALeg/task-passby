# 同类工作多次执行：Memory 基准与五次工作序列

核查日期：2026-09-10。本文核查相关论文的评测设置及作者实现；AgentMemoryBench、STATE-Bench 和 LongMemEval-V2 的补充判断主要依据官方仓库协议。未运行这些基准，不报告排行榜提升。论文尽量引用固定版本，代码链接为本次查看的 `main`，复现时应固定提交。

**并非没有跨独立任务执行的 Memory 评测。** AWM Online、LifelongAgentBench、AgentMemoryBench Online 都涉及先前执行经验对后续新实例的影响；Continual Learning Bench 的 ICL Notepad 配置更明确地清空实例之间的聊天、保留笔记和反馈。因此，“重新开始会话但延续经验”已经有直接先例。

用户提出的具体单位是：**同一用户的一类工作，在五个独立实例中使用新输入、分别交付、接收反馈，并持续保留适用经验。** 在本次核查范围内，既有协议覆盖了其中多项条件；不能把它们直接等同于真实用户一周工作的完整评测，也不能据此宣称这个研究方向空白。

| 评测安排 | 它主要验证什么 | 与五次工作序列的区别 |
|---|---|---|
| 读取多会话历史后回答问题 | 历史信息能否保留与使用 | 没有逐次执行新工作产生自己的经验 |
| 同一输入独立运行五次 | 可靠性、输出波动 | 五次不构成在线学习链 |
| 同一问题失败后反复尝试 | 利用反馈修正当前解法 | 后一次仍是同一问题 |
| 一个大目标分多个会话完成 | 依赖状态能否跨会话保留 | 不一定是同类工作的独立交付 |
| 顺序执行同类新实例并更新记忆 | 经验能否迁移到下一次工作 | 最接近；还需检查用户身份、反馈和验收设置 |

## 已有跨实例学习研究

### Agent Workflow Memory：在线版本符合跨任务经验积累

Wang 等，2024-09-11，arXiv v1。AWM 是方法，在 WebArena、Mind2Web 上评测。离线版先从训练轨迹提炼固定工作流；**在线版依次完成不同测试任务，将模型评估器判断成功的轨迹抽象为工作流，加入记忆供下一任务使用**。工作流会移除具体商品等实例值；任务按网站分组。[论文 §2.3、§3](https://arxiv.org/html/2409.07429v1)

作者 WebArena [pipeline.py](https://github.com/zorazrw/agent-workflow-memory/blob/main/webarena/pipeline.py) 为每个任务另起 `run.py` 进程，完成执行、评估、更新工作流文件三步。因而这里有新任务执行上下文和持续文件记忆，不是一直延长原聊天。WebArena 真实操作托管网页，以功能成功评分；Mind2Web 的逐步预测评分不能混称端到端网页执行成功。在线记忆默认依据模型判断，作者也提供改用 ground-truth reward 的选项，二者必须区别。[作者执行说明](https://github.com/zorazrw/agent-workflow-memory/tree/main/webarena)

局限：同网站不等于同一用户、同一业务工作；未测每天一次的真人反馈。它证明已有“先前执行经验→后续新任务”的评测设计，不能证明五次内必然进步。

### LifelongAgentBench：新 session 加此前成功轨迹

Zheng 等，初稿 2025-05-17；核查 v3，2025-05-30。包含 DB 500、OS 500、KG 396 个任务，以共享技能连接不同实例并严格顺序执行。实际执行 SQL、Bash、知识图谱查询；OS 每任务重建容器，DB 清理任务表。评分看任务是否正确完成，环境产生成功/失败反馈。[论文 §3–6](https://arxiv.org/html/2505.11942v3)

上下文边界有代码证据：`on_session_create` 断言新 session 的 chat history 为空，再将此前保留轨迹放入新提示；`on_task_complete` 只接收被评为 `CORRECT` 且 `COMPLETED` 的任务，超过容量时淘汰最早一项，并支持存盘恢复。因此是在线跨实例回放；**成功标签参与记忆筛选**，不能当成完全无外部反馈的自学习。[作者回放实现](https://github.com/caixd-220529/LifelongAgentBench/blob/main/src/callbacks/instance/previous_sample_utilization_callback.py)

局限：基线主要回放近期成功轨迹；共享的是 SQL/Bash 等技能，未固定真人身份、偏好与工作日。它能检验经验迁移，不直接衡量用户少改了几次稿。

### MemoryAgentBench：两阶段学习，不是逐次交付后成长

Hu、Wang、McAuley，初稿 2025-07-07；核查 v4，2026-06-28。对应 [HUST-AI-HYZ 作者仓库](https://github.com/HUST-AI-HYZ/MemoryAgentBench)，需与名称顺序相反的 AgentMemoryBench 区别。协议先逐块输入历史、增量更新记忆，全部输入结束后才测相关问题；外部工具主要服务记忆构建与检索，不是浏览器购物或仓库修复执行。[论文 §3.3](https://arxiv.org/html/2507.05257v4)

它也不应整体被贬为事实回忆：TTL 子项要求从带标签示例学习分类规则，或从电影对话学习推荐模式，再泛化到未见输入；指标包括分类正确率、推荐 Recall@5。其他子项测检索、长程理解、选择性遗忘。**v4 附录 H.1 明确把 acquisition 与 evaluation 分开，并承认省略了交错的执行—反馈—记忆修正循环。** 因此历史可以包含多轮、多会话，仍不能据此声称测过“任务一交付后的新经验帮助任务二”。标签来自预设示例，未固定同一真实用户周序列。[论文附录 B.2、H.1](https://arxiv.org/html/2507.05257v4)

### Continual Learning Bench：最贴近的协议之一，须按系统区分重置

Asawa 等，2026-06-04，arXiv v1。一个 task 指一整串相关 instances；每个 instance 独立产生奖励，共享可学习的代码库、数据库规则或对手策略。Codebase Adaptation 包含两个仓库的 19 个不同 issue，每个从各自 base commit 的新 Docker 容器开始，通过 Bash 修复，并由隐藏回归测试和求解步数评分。不同实例真实执行并产生环境反馈，属于跨实例迁移。[论文 §3–4、附录 A.2](https://arxiv.org/html/2606.05661v1)

它没有统一要求清空聊天：论文中的 ICL 保留历史，Claude Code/Codex 使用每条序列的持续 conversation；而 [ICL Notepad 说明](https://github.com/pgasawa/continual-learning-bench/tree/main/src/systems/icl_notepad) 和 [实现](https://github.com/pgasawa/continual-learning-bench/blob/main/src/systems/icl_notepad/system.py) 明确默认在实例边界清空消息与 provider 状态，保留模型更新的 notepad，并把末尾反馈带到下一实例。这个配置直接支持“上下文重置、经验持续”。

评分同时看交付 reward 和同实例上 stateful 减同系统 stateless 的 gain，以减轻任务难度变化造成的假进步；论文的五次 rollout 是重复整条评测序列，不是五个工作日。共享仓库/环境可对应稳定工作类型，尚不等于同一真人的偏好、澄清负担和验收。[论文 §4–5](https://arxiv.org/html/2606.05661v1)

### 对五次独立工作的有限启发

可以借用 AWM 的执行后更新、LifelongAgentBench 的新 session 与可追踪经验、CL-Bench 的逐实例对照。要另行规定固定用户、工作类型、每次新输入、反馈可见范围和交付验收；清空聊天时也须检查工具状态和文件是否泄漏前次答案。MemoryAgentBench 可做记忆能力诊断，不能替代交付评测。以上是协议适配建议，不构成“这一研究方向尚无人做”的证据。


## 补充核查：对话记忆、工作经验与在线执行的区别

### LoCoMo 与 LongMemEval：跨会话历史不等于跨工作执行

LoCoMo 原始数据包含按时间组织的多会话长对话，同时提供问答、事件摘要等标注；不能把它说成“只有彼此独立的一问一答”。LongMemEval 则为每道评测题提供带时间戳的聊天历史，要求处理多会话信息、更新、时间关系及未知情况，最后回答问题。二者说明了历史可以很长、可以跨会话，但这不等于被测 Agent 自己每天完成一项新工作，并利用实际交付反馈改善下一次表现。[LoCoMo 作者仓库](https://github.com/snap-research/locomo)、[LongMemEval 作者仓库](https://github.com/xiaowu0162/LongMemEval)

### AgentMemoryBench：已经有顺序执行、在线更新的直接反例

此处是 solomoon313 的 **AgentMemoryBench**，不是 HUST 的 **MemoryAgentBench**。作者仓库明确给出 Online、Offline、Replay、Transfer、Repair 五种模式，覆盖数据库、Shell、知识图谱、ALFWorld、WebShop 和 LoCoMo。Online 按顺序处理样本、更新记忆并记录表现；不同子数据的执行和评分方式仍不同，不能把 LoCoMo 子项也称作工具执行任务。[作者仓库及协议](https://github.com/solomoon313/AgentMemoryBench)

代码进一步支持这一判断：调度器支持单类样本按顺序、类内打乱、跨类混排；工具任务由 `start_sample` 取得本次会话的初始消息，运行结束后以本次轨迹和结果更新记忆，再进入下一个样本。其 Online 模式是用户所述“连续但分离”的直接相邻设定。不过，仓库没有据此建立“同一真实用户、同一种日常交付、五天真实工作”的数据收集协议。这里核查了 README、调度器和 runner，未运行基准；所述为访问时 main 分支实现，不把仓库中的投稿文件名当作会议录用证明。[调度器](https://github.com/solomoon313/AgentMemoryBench/blob/main/src/client/scheduler.py)、[执行与更新流程](https://github.com/solomoon313/AgentMemoryBench/blob/main/src/runner/main.py)

### MemoryArena：行动与记忆形成循环，但任务之间有显式依赖

MemoryArena v1 §3.2 规定一个评测 episode 内有多个独立 session，各 session 完成后更新持久记忆；episode 开始时记忆为空。购物子集固定为六次购买，后续物品须兼容前面买到的物品。论文还包括增加参与者的旅行安排、渐进搜索和形式推导。它确实测跨会话行动与记忆，也包括部分可独立完成的购买动作；其主要设计强调子任务之间的因果依赖，整体 episode 的成功取决于这条依赖链，和同一种日报每天处理新输入的经验迁移仍有区别。长上下文对照可以保留原始历史，不能将所有方法统称为彻底删除历史。[论文 v1，§3.1–3.2、§4.1](https://arxiv.org/html/2602.16313v1)

### STATE-Bench：经验迁移存在，“五次”不能误读为成长序列

Microsoft 的 STATE-Bench 当前 Agent Learning Track 在每个领域提供 100 份训练轨迹和 50 个留出测试任务，允许从训练轨迹提炼记忆、技能或提示优化产物。测试时通过只读检索接口获取经验，再在模拟用户、领域工具和任务局部数据库中实际执行。它测试已有经验是否改善新任务，当前公开协议不是边做第一个测试任务、边更新记忆以影响第二个测试任务的在线成长协议。[Agent Learning Track](https://github.com/microsoft/STATE-Bench/blob/main/docs/AGENT_LEARNING_TRACK.md)

该基准要求每个任务运行五次：`pass@1` 汇总单次成功率，`pass^5` 检查五次是否全部成功。这是重复试验下的可靠性；不能因为出现“五次”就认为它对应用户提出的五个不同日常工作实例。任务数据为合成数据，用户由模拟器扮演。官方成本指标也不会自动计入所有离线经验构建成本，我们自己的实验应另计这些成本。[README 与指标定义](https://github.com/microsoft/STATE-Bench)、[记忆接口](https://github.com/microsoft/STATE-Bench/blob/main/docs/memory/builtin-hook.md)

### LongMemEval-V2：已经使用工作轨迹，主要评分仍是问答

2026 年的 LongMemEval-V2 使用多模态网页 Agent 轨迹，包含工作流知识、环境常见陷阱、状态变化等问题。因此，“Memory 数据都只来自聊天”也不准确。但公开基准让记忆系统读取既有轨迹、为后续问答返回依据，主要测答案准确性与查询延迟；这与在线完成下一项工作及其交付验收仍应分开。[作者仓库](https://github.com/xiaowu0162/LongMemEval-V2)、[论文](https://arxiv.org/abs/2605.12493)

## 如何把一周五次工作变成可解释的评测

以下是针对 Worket 的研究方案，尚未执行，也不是已经确认的产品改动。

评测单位可以定义为“一个用户的一类工作，按时间排列的五个独立实例”。五次具有共同的工作目的、交付类型和部分长期规则，但每天使用新的输入，产生各自可验收的结果。若只是相同输入重跑五次，主要测稳定性或同题重试；若把一项未完成的工作拆成五段，则主要测继续执行与状态保持。两类都可以作为对照，不能替代主序列。

| 次序 | 主序列安排 | 观察重点 |
|---|---|---|
| 第 1 次 | 第一份真实输入，允许必要澄清，完成交付并接收反馈 | 初始理解与沟通成本，哪些经验值得保留 |
| 第 2 次 | 新输入、新会话，延用适用的长期要求 | 是否减少重复说明，是否套用旧事实 |
| 第 3 次 | 第三个新实例，使用此前自己的执行与反馈记录 | 修正是否落实到交付，是否形成错误泛化 |
| 第 4 次 | 第四个新实例，继续按相同规则验收 | 收益是否稳定，是否反复犯同类错误 |
| 第 5 次 | 未见的新输入，完成第五次独立交付 | 后续表现相对无记忆对照的差异及整周总成本 |

主序列先保持规则稳定，另建扰动版本检查：一次性例外是否误变成长期规则；明确的新规则能否覆盖旧规则；穿插无关工作后是否串用记忆。更换执行器也应作为单独条件，不在基础实验里同时更换模型、工具与记忆，以免无法解释差异。

**独立会话需要落实到可见信息。** 每次重建模型会话及本次运行状态，只有事先声明的持久渠道可以跨次访问，包括记忆库、已确认工作定义、允许保留的材料和记录。文件、缓存、旧输出同样可能成为记忆渠道，应统一记录；原始历史全文也可以作为一种明确的记忆基线。模型参数固定时，这里测试的是 Agent 系统利用经验的收益，不是证明基础模型权重在持续学习。

**执行顺序为：先完成本次并评分，再接收当时可获得的反馈、更新记忆，再开始下次。** 不允许第五次的结果、反馈或标准提前进入前四次记忆。可使用模拟日期验证协议；如果结论涉及真人的每日使用负担、跨天环境变化或定时机制，则需要真实历时观察。

## 两种互补实验，避免把不同问题混成一个分数

**相同历史下的迁移测试。** 固定前四次真实工作记录作为各方法共同的输入，只提供第五次的新输入并要求完成交付。它适合比较不同记忆表示和 Abstract 产物的利用效果，但不能证明系统自身在前四次执行中逐步变好。

**闭环在线序列。** 各方法从相同起点执行五个相同的新实例，每次只继承自己之前得到的记录与反馈。预先规定同样的任务条件和反馈原则，而不是强行给不同错误发送同一句反馈。这更接近真实使用，但轨迹会分叉，需要多个用户／工作序列并进行配对比较。

最小对照包含：每次清空历史、可访问原始历史、现成 Memory、相同 Memory 加明确 Abstract 流程。普通模型的自然澄清能力及现成 Memory 的原生归纳能力都保留。最后一组应遵守用户主动沉淀、确认可复用定义的产品边界；确认耗时计入成本。如果直接注入人工写好的完美定义，只能标作理想条件或辅助对照，不能算自动 Abstract 的收益。

## 应该报告什么

| 指标 | 它能回答的问题 |
|---|---|
| 每次首次可接受交付的质量与完成情况 | 后续独立工作是否做得更好 |
| 解释、澄清、审阅、纠正和返工的总时间 | 用户是否真的省力，而非前置填写更多内容 |
| 已纠正问题在后续实例的重犯次数 | 是否学会并保留了有效经验 |
| 旧事实误用、临时例外扩散、持续规则遗漏 | 记忆是否污染新工作 |
| 每次及累计模型、检索、记忆构建成本 | 改进是否值得其额外成本 |
| 每条序列的逐次表现及失败轨迹 | 哪一阶段开始受益或退化，平均分掩盖了什么 |

不能只比较“第五次分数减第一次分数”，因为每天输入难度不同。应在相同实例上比较有记忆与无记忆条件，再汇总每个位置及整条序列的差异。前五次中后续轨迹依赖此前经历，不能当作五个完全独立统计样本；正式推断应以用户或工作序列为单位处理相关性。一条五次序列适合发现机制与明显失败，不足以单独证明普遍产品收益。

这项研究可以采用已有跨任务学习基准的协议，再补入我们关注的同一用户、稳定工作类型、真实交付、规则适用范围和用户成本。当前核查足以否定“没有跨执行记忆评测”，不足以证明覆盖全部条件的研究从未存在。
