# Abstract 与 Memory 的边界

**建议把 Abstract 定义为“形成并检验工作约定的过程”，把 Memory 定义为“跨时间保留、更新和调用信息与经验的能力”。** 两者处在不同维度，技术上大量重叠。Abstract 可以利用记忆、生成记忆，也可以在没有历史的第一次对话中发挥作用；Memory 系统同样可以包含推断、抽象和反思。

对 Worket 有用的职责边界，是从“系统有理由这样理解”走到“这项工作应该据此开展”。这里包含本次适用性、冲突处理、完成标准和授权依据。它是产品设计建议，并非学术界已统一接受的术语定义。

## 1. “未说出的话”有几种不同来源

| 情况 | 例子（均为构造案例） | 系统需要做什么 | 不能自动得出的结论 |
|---|---|---|---|
| 以前说过，这次省略 | 过去明确要求报告中的事实附来源；这次只说“照之前做” | 在授权范围内找回原约定，检查是否适用和过时 | 历史中的全部细节都要继承 |
| 没有直接说过，但存在行为证据 | 多次删掉宣传口号、保留具体数字 | 提出“偏好具体证据”的有来源假设 | 用户永久讨厌所有修辞 |
| 当前表达需要情境解释 | “做得像咨询公司一点” | 区分论证结构、数据密度、视觉风格等候选含义，用小样确认重要差异 | 自动等同于黑白配色、固定页数或某种框架 |
| 目标或偏好尚在形成 | 看过两个方案后才发现真正担心的是可信度 | 帮助比较取舍，记录新决定和理由 | 可以从旧记忆恢复一个原本就完整存在的答案 |
| 行动权限尚不清楚 | “把这个事情推进一下” | 根据现有有效授权界定可做的动作；缺失且影响外部行为时定向澄清 | 曾经批准一次外发，就永久批准所有外发 |

前两类最明显地与记忆交叉；后三类常需要本次互动。但这不是排他分类：同一次澄清可以同时找回事实、形成偏好并修订任务。人类研究也提示，理解只需达到当前协作所需的程度，偏好和评价标准有时会在互动中形成。详细依据见 [人类问题形成研究](human-problem-formulation.md)。

## 2. 现有 Memory 已经会做抽象

Mem0 原论文把写入分成抽取和更新两个阶段，使用模型比较候选信息与既有记录，再决定新增、更新、删除或不变。因此，用“有没有模型推理”区分 Memory 和 Abstract 从一开始就不成立。[^M1]

A-MEM 在生成笔记和关联之外，还会根据新经验更新已有记忆的上下文、关键词和标签，使更高层的模式出现。该论文研究的是记忆组织和后续问答表现，不能据此宣称已经解决工作约定的用户确认与业务验收。[^M2]

产品层面，Mem0 Dream 的 Synthesis 已明确提供跨记忆模式归纳，并把新模式与来源记忆关联。这是“从散落的信息中说出未直接说过的内容”的直接重叠案例。官方功能说明能证明能力范围的声明，不能证明推断对真实用户始终成立。[^M3]

Letta、LangMem 和 Graphiti 的官方实现也说明，Memory 已涉及内容编辑、程序经验与时态关系，不能统一描述成静态向量库。Zep Observations 还可归纳决定、承诺和约束，未来目标与持续性要求也可以进入记忆。[^M9] 产品版本及各自边界见 [产品与协议对照](product-and-protocol-landscape.md)。

**因此，假如某个 Memory 产品进一步支持任务范围裁定、要求修订、验收和复用，它就在覆盖 Worket 的目标能力。** 是否存在竞争取决于实际工作流程，不能靠换一个名称制造区别。

## 3. 更有用的区别是“知识依据”与“工作约定”

下面比较的是两种职责，不是断言所有产品只能属于某一栏。

| 维度 | 作为 Memory 的职责 | 作为 Worket Abstract 的建议职责 |
|---|---|---|
| 核心问题 | 哪些信息、经验与持续性约定值得跨时间保留，并在此刻调用？ | 当前或下一类工作应达成什么，哪些依据可以成为要求？ |
| 组织中心 | 用户、实体、事件、关系、经验、会话等 | 一项工作或一类可复用工作的输入、交付与约束 |
| 合理输出 | 事实、偏好、推断、经验、目标、承诺、规则及其来源和更新关系 | 可审阅的任务候选、仍有影响的歧义、验收办法 |
| 有效性的检查 | 是否准确、有来源、相关、不过时？ | 是否适用于此工作、表达真实取舍、能够执行与判定？ |
| 信息地位 | 保存一条推断，仍可是一条推断 | 推断成为本次要求时，须有明确采用依据 |
| 变化方式 | 随新证据更新当前理解，同时可保留历史 | 草稿可演化；已生效约定的变化应可解释，已发布定义版本固定 |
| 主要失败 | 丢失、误记、过时、串人、相关信息没有被使用 | 擅自补目标、错定工作边界、错误继承、验收脱节、扩大权限 |
| 效果检查 | 检索、记忆问答、更新处理、个性化表现 | 意图保真、实际交付、用户说明和修正成本、过程边界 |

“用户通常喜欢短报告”可以是一条准确记忆。“本次向董事会提交的报告最多三页”是一项具体要求。两者之间需要情境与理由：也许这次必须展示风险明细，也许读者完全不同，也许旧偏好只针对周报。

**有来源解决的是“为什么这样认为”；有采用依据解决的是“为什么这次照此执行”。** 明确的持续性要求，在适用范围内可以直接沿用；本次已明确授权的行为，也不应反复询问。只有推断、新范围或实质冲突需要额外处理。

## 4. 不能从回忆正确直接推导出任务定义正确

LongMemEval 的 500 个问题覆盖信息提取、跨会话推理、时间推理、知识更新和对未知信息的拒答。它把“找得到”与“用得对”分开分析；这对 Worket 很有启发，但其核心任务仍是基于历史回答问题。得到高分不足以证明系统能帮助真人形成尚未确定的目标。[^M4]

PrefEval 更贴近“未说出的话”：它检查明确和隐含偏好的推断、记忆和遵循。数据由 1,000 种偏好的三种表达形成 3,000 对偏好与问题，隐含对话从预设偏好生成；因此它可以检查恢复与遵循，不能覆盖全部“用户边做边发现自己要什么”的情况。[^M5]

PersonaMem 考察用户信息随时间变化，以及在新场景中的个性化响应。其模拟历史有助于构造可控实验，但模拟画像不是现实用户的开放意图；预测最合适回应，也没有直接检验任务范围、过程权限和真实交付。[^M6]

对现有系统的批评必须保持这个尺度：这些评测没有测某项能力，不等于这些系统做不到；论文中的旧模型表现，也不能当作今天产品的能力排名。

## 5. WorkDefinition 可以是一种受到约束的组织记忆

从保存并复用经验的角度，已确认的 WorkDefinition 确实属于组织记忆的一部分。它与普通经验笔记的差别，在于它明确表达一类工作未来开展时的约定，并通过新实例验证其适用性。

现有 Worket 的 [领域术语](../../../CONTEXT.md)、[定义契约](../../../src/contracts/definition.ts) 和 [沉淀规格](../../specs/work-distillation-v1.md) 已提供以下基础：

- `WorkDefinition → WorkInstance → WorkRecord` 把工作类别、一次工作和事实记录分开；换执行者保持同一次工作，复用产生新实例。
- 七类定义内容覆盖目的、输入、交付、约束、验收、方法与资料；每项支持来源或推断依据。
- 候选定义与固定发布版本分开，方法区分参考和必需，缺失信息与冲突可作为问题保留。
- 用户主动沉淀并确认定义；旧客户、本次例外和临时授权不默认进入下一次工作。

这些是对当前文件的核对，不代表真实业务效果已经通过验收。现有 [产品文档](../../product.md) 与 [执行依据](../../work-object-extraction-execution-plan.md) 仍明确保留真实第二次工作的效果验证。

将研究映射到产品，可以形成一个循环：

```text
授权范围内的记录与已有记忆
        ↓ 找回证据、判断时效与适用范围
当前表达 + 候选目标、约束和隐含要求
        ↓ 处理有实质影响的差异；必要时给小样
本次工作约定 + 验收办法 + 有效行动范围
        ↓ 实际工作中的新证据与用户修正
工作记录
        ↓ 用户主动决定沉淀
已确认的 WorkDefinition 版本
        ↓ 新输入、适用性检查
下一次工作
```

图中的“本次工作约定”是研究用概念，没有要求新增同名领域实体，也没有把普通对话的每次澄清都变成发布定义。当前工作的要求形成，与跨实例的可复用定义发布，可以共用抽象能力，仍应保留不同生命周期。

## 6. 一次可观察的示例

以下完全是构造案例，用来展示需要验证的行为。

**当前表达：**“帮我把这份材料做得像咨询公司一点，老板一眼就知道该不该投，别太虚。”

**已有授权记忆：**过去几次投资讨论中，用户要求关键判断有资料出处；曾有一次因赶时间接受五页简版。该次五页要求没有被确认成长期偏好。

记忆提供的两条历史依据是“重视证据”和“五页简版曾被接受”。它们的作用不同，后者不能直接成为本次页数上限。即使 Memory 已能生成更高层解释，仍要检查它如何影响本次要求。

Abstract 的候选表达可以是：“这份材料用于支持老板决定是否继续投入；建议围绕客户问题、验证证据、收益与成本假设、主要风险和下一步验证组织。‘像咨询公司’暂解释为结论先行、论据可查；视觉风格先用简洁默认值。”

这里的“用于决定是否投入”来自当前明确表达；结构是助手的提案；“论据可查”有历史和当前表达的共同支持；视觉是可逆默认值。产品应该允许用户看懂这些不同地位，而无需逐句确认。

真正会改变工作方向的缺口可能是“这次在决定立项，还是批准下一轮试点预算”。若材料或现有对话能回答，先读取；若不能，一次定向澄清通常比询问字体、角色设定和页数更有价值。

形成工作候选后，再约定验收：关键判断能追溯；假设与事实可区分；读者能找到需要拍板的事项。未知商业事实可以作为待验证项，不能靠补写确定结论填满报告。

**授权独立处理。** “给老板看”不自动等于“立即替我发给老板”。如果当前已有覆盖这次收件人和材料的有效发送授权，就按该授权执行；如果没有，则先完成可审阅产物，在发送所需的节点处理缺口。

## 7. 权限不应成为普通偏好记忆

关于 Agent 用户权限的 2026 年研究，将用户界面的许可表达、内部政策生成和运行时执行分开分析。论文整理 21 项方案并比较 5 个商业 Agent，说明“用户说过一句话”与“系统实际限制动作”属于不同层面。它是研究者的综述与观察，不是产品安全认证。[^M7]

AuthBench 又把“根据任务推导权限”作为单独问题：120 个终端任务中的模型会同时漏掉必要访问并授予多余访问。该结果只覆盖文件级读、写、执行，不能直接外推到所有 API 或企业业务。它支持我们单独评价授权边界，而不是只看最终任务是否完成。[^M8]

建议把下列信息分开保存：

| 类型 | 示例 | 使用规则 |
|---|---|---|
| 偏好 | 通常希望输出简洁 | 作为可被本次需求覆盖的默认倾向 |
| 持续性要求 | 公司规定外发报价必须经财务复核 | 在已核实适用范围内作为过程约束 |
| 实际授权 | 指定主体允许向指定收件人发送某份材料 | 检查动作、对象、条件、有效期与撤销状态 |
| 行为历史 | 上次系统曾发送过一份报价 | 作为历史事实，不能独自产生本次许可 |

这不是要求增加批准次数。恰当的记忆应当减少重复申请已有权限，同时避免把过去发生过的行为误认为长期授权。

## 8. 如何用实验验证两者的增量价值

建议采用同一底层模型、工具、执行环境与资源预算下的 2×2 对照。这里的 Abstract 条件包含明确的任务候选、处理关键歧义和验收约定；Memory 条件使用相同范围内的可用历史。“无 Abstract”只表示不启用本研究的显式工作约定流程，仍保留 Memory 原有的归纳、规则学习和执行器的自然澄清能力。

| 条件 | Memory | Abstract | 检查的问题 |
|---|---|---|---|
| A | 无 | 无 | 原始表达的基础表现 |
| B | 有 | 无 | 记忆本身解决了多少遗漏与重复说明？ |
| C | 无 | 有 | 没有历史时，任务形成过程有没有价值？ |
| D | 有 | 有 | 两者组合是否改善结果，还是只是增加流程？ |

普通执行器已有的自然澄清能力应保留，不能故意禁用来制造弱基线。再增加一个“只把原话整理成清晰文本”的辅助基线，检查收益是否只来自重排语句。各条件的交互额度与总资源应预先记录；若实际用量不同，同时报告成本，避免把额外计算当成独有设计效果。

评价至少包含三组结果：

1. **任务定义质量：**关键要求保留率、无依据新增要求、过时信息继承、工作边界错误、重要未知是否暴露。
2. **实际工作质量：**首次可接受交付、可接受变体、过程义务和有效授权的遵循。检索准确不能代替这一组。
3. **用户总成本：**初始说明、回答问题、审阅候选、修改错误、验证交付和返工的时间；同时记录问题数、退出和主观负担。

先用少量真实工作定位错误；正式比较时按用户与工作类别划分留出，防止同一用户的偏好或同类答案泄漏。没有真人互动时，只能报告模拟条件下的结果。某个实验组在某类任务没有增量，也应当被接受为有效结论。

## 9. 对定位的实际影响

Worket 可以使用现成记忆基础设施，也可以把已确认定义作为一种工作记忆输出。核心研究问题应收敛到：**怎样以尽量少的用户负担，把散乱证据和当前意图形成可靠工作约定，并让后续执行证明这份约定有用。**

最值得检验的差异包括：工作范围是否比会话范围更合适；模型补出的要求是否有可理解的依据；用户是否能低成本修正；定义能否在新任务、新执行者和新情境下继续有效。它们都需要实际对照，不能从“可追溯”“结构化”“跨 Agent”这些能力标签直接推导商业优势。
