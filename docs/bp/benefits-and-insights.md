## B001 — 工作授权与可替换执行者

### 讨论起因与用户观点

讨论 Zep 的项目隔离、RBAC、API Key ABAC 和 UserGroup 后，用户认可项目隔离可能必要，担心把 Agent 当成固定岗位或角色逐一配置权限，会让组织在引入、升级、拆分或合并 Agent 时不断维护角色与授权。用户提出：这种随 Agent 能力变化而调整角色的方式，可能难以满足 AI-native 组织的灵活性。

记录其核心问题：企业如何持续吸收更强的 AI 执行能力，同时避免每次调整执行者都重新配置组织权限？上述复杂度判断是用户提出的设计问题，尚不能据此断言 Zep 无法支持 AI-native 组织。

### 已核实的竞品事实

核实日期：2026-09-10；范围：Zep v3 官方文档。

- 普通 API 请求按 API Key 所绑定的策略授权。一份策略集可以绑定多个 Key，一个 Key 可以绑定多份策略集；其 `role` 指 `default_allow` / `default_deny` 两种初始权限立场，不等于为每种 Agent 能力建立业务岗位。
- 文档没有要求每个 Agent 另建终端用户，也没有要求每新增或升级一个 Agent 都新增角色或策略。权限配置成本取决于调用方如何管理身份、凭据与策略绑定。
- UserGroup 当前治理 Memory MCP 用户对共享独立图谱的访问，普通 API Key 流量不受用户组策略影响。后台人员的 RBAC 是另一条管理路径。

来源：[Agent access](https://help.getzep.com/attribute-based-access-control)、[UserGroup access](https://help.getzep.com/usergroup-access)、[Managing team access](https://help.getzep.com/role-based-access-control)。

### 对 Worket 的洞察

工作的目标、责任和授权范围通常比承担工作的具体 Agent 更稳定。如果权限主要围绕某个长期固定的 Agent 岗位配置，执行分工变化可能带来额外维护；可以探索让具体工作的授权约束保持稳定，由可替换执行者在该范围内承担执行。

当前项目依据：[CONTEXT.md](../../CONTEXT.md) 已将 WorkInstance、Executor 和 ExecutionEpisode 分离，交换执行者不改变工作身份；[产品文档](../product.md) 与 [架构文档](../architecture.md) 描述了这一接力基础。现有材料不能证明 Worket 已实现企业级动态工作授权。

### 助手提出的设计设想（待讨论，未批准实现）

保留组织、项目和资源边界；由有权委托的人或组织为本次 WorkInstance 确定允许访问的资料、操作、期限和责任。执行时，系统结合当前策略与执行环境约束签发受限授权，并记录本次执行者。授权由可信应用执行，不由模型自行声明。

更换执行者时，在工作范围不变的前提下重新校验并签发授权，尽量复用已有约束，不要求业务人员为每种 Agent 能力手工建立永久岗位。新增数据、操作或委托范围仍须重新授权；Agent 更强不意味着权限自动扩大。新执行环境的身份接入与信任检查仍然必要。

工作定义可表达授权需求，但下一次复用不能继承上次的临时授权或客户访问权；这一边界与现有“本次输入”约定一致。撤销只能阻止后续访问，不能保证收回已交给外部执行者的数据。

### 用户价值与 BP 候选表达

潜在价值：企业可以持续更换、组合或升级 AI 执行者，同时减少重复权限配置，并保留工作责任与审计连续性。配置成本是否下降，需要实际比较。

候选表述（方向性，不能作为当前能力宣传）：**Worket 希望让企业围绕工作保持责任与授权边界，在边界内持续升级 AI 执行方式，降低组织吸收新能力的调整成本。**

### 可展示场景与验证要求

以“为客户 A 准备报价草案”为例：工作允许读取客户 A 的指定资料并生成草稿，发送报价需要单独批准。先由 Agent A 执行，再换 Agent B，或拆给两个执行者协作；工作身份和验收标准保持不变，各执行者仅获得其执行范围内的授权。

待验证：换执行者需要多少次人工配置；拆分任务是否能限制子任务权限；旧授权是否失效；客户 B 的资料是否不可访问；发送操作是否仍需批准；能否追溯委托人、执行者、授权版本与操作结果。应与复用策略或自动绑定策略的方案比较，不能只与“每个 Agent 手工新建角色”的低效配置比较。

尚缺证据：企业用户是否实际遇到这一成本，当前 Worket 是否能端到端执行上述约束，以及它相对其他方案带来的可量化收益。

## B002 — 用后续工作的交付效果验证沉淀价值

### 讨论起因与研究事实

用户要求解读 MemOp；本条是助手据此提出的产品洞察，尚未经过用户确认。

2026-09-10 核实：[项目页](https://xhguo7.github.io/MemOp/)、[论文 v1](https://arxiv.org/html/2606.05646v1)、[官方代码说明](https://github.com/xhguo7/MemOp)。MemOp 将执行轨迹转成记忆候选，用有无记忆的执行结果筛选候选，再训练独立的记忆生成模型。它评估单次轨迹再利用与跨任务记忆演化；主要验证范围是 Python 仓库中的软件修复任务。

### 对 Worket 的洞察与当前依据

沉淀的内容是否忠实、用户是否确认，以及下一次使用是否改善交付，是三个不同问题。确认适合保存的工作定义，不等于证明它能减少返工或提高交付质量。应将后续复用与验收反馈关联回定义版本，才有依据决定哪些抽象值得保留、修订或停止推荐。

当前依据：[产品文档](../product.md) 已要求第二次真实执行验证，并描述了来源、候选、人工修改、定义版本、复用和验收反馈的采集链；同一文档明确真实样本版本效果比较尚未完成。这是评测基础，不是收益证据。研究记忆也不等于 WorkDefinition；工作约定、原始记录和执行经验仍须区分。

2026-09-10 补充：用户询问开发者能否获得使用者与 AI 的聊天记录；这一问题不代表授权新增采集。当前代码核实：普通记录保存在使用者本机；沉淀所选材料经过配置的后台与模型供应商处理，但只有另行勾选“参与改进 Worket”才进入管理员可查看的样本库，授权起保存 90 天。客户端必须连接该管理员管理的服务并成功同步，安装应用本身不等于上报。依据：[桌面授权与样本登记](../../src/distillation/desktop.ts)、[服务连接](../../src/ai-service/client.ts)、[改进样本说明](../../server/README.md)。本次未核实线上部署或真实用户样本到账情况。

2026-09-10 用户后续明确：非常需要真实使用情况作为后续优化的数据基础，要求参与改进默认勾选、直到用户取消，并希望安装后直接连接后台；随后将交付边界调整为先修改，不发布、不打包，待前端优化后再打包。默认偏好与停止行为本轮修改源码；自动接入仍待确定后台地址和首次身份接入方式，不能表述为真实样本已经自动到账。此前“另行勾选”描述对应旧版行为。

助手补充的价值判断（待验证）：产品改进的评测价值取决于授权材料能否关联候选、人工修订与后续验收，不能用聊天记录总量代替质量证据。可展示同一授权样本从来源到修订、验收的过程及停止、删除入口；真实覆盖率、反馈质量和改进收益仍须试点验证。本条不增加授权范围或批准训练。

2026-09-10 部署补充：根据用户提供的 VPS，已实现独立安装自动接入并实测可信 HTTPS、六类合成事件收集、管理员查看、跨安装隔离、停止与删除；桌面取消选择重启后保持。后台上线与桌面发布独立进行，当前未打包发布、模型配置待授权，不能表述为真实用户数据或改进收益已经取得。证据：[VPS 部署验收](../deployment/vps-operation.md)、[实时数据链路脚本](../../scripts/qa-vps-samples.mjs)。助手提出的价值方向：减少参与改进的连接配置成本，同时保留可追溯的安装身份和退出控制；是否提高真实反馈覆盖率仍待试点验证。

2026-09-11 状态更新：用户明确同意模型 Key 迁移，已完成 VPS 加密配置及真实 DeepSeek 调用验收。合成周报案例从真实模型候选、修改发布到复用和合成成果验收形成六类事件回传；停止、删除、客户端和服务端重启恢复均通过。该结果验证了数据闭环可运行，尚不证明真实用户覆盖率、真实第二次交付或改进收益；初次失败暴露的目标字段格式和引用片段问题已通过明确提示修复，契约校验没有放宽。证据：[真实模型验收记录](../deployment/vps-operation.md)、[桌面公网脚本](../../scripts/qa-vps.mjs)。

2026-09-11 采集覆盖边界复核：用户询问新版能否把使用者对话上传服务器。当前代码支持沉淀时将所选对话材料及后续修订上传改进样本库；复用仅回传定义、非文件输入和验收反馈，不回传新工作对话。普通记录没有通用对话上传入口，默认参与改进不等于全部聊天自动同步。本轮公网 `/health` 实测返回 `ok:true, configured:true`；GitHub 最新发布仍为 2026-09-09 的 `v0.1.1`，部署记录明确新版桌面未打包发布。已有合成材料闭环证明链路可运行，真实用户到账仍未验证。产品判断：若优化需要普通记录中的对话样本，当前沉淀触发机制的覆盖率是否足够须单独验证；本次询问不代表批准扩大采集范围。依据：[采集触发](../../src/distillation/desktop.ts)、[用户范围说明](../../src/renderer/distillation.ts)、[部署记录](../deployment/vps-operation.md)。

2026-09-11 用户明确要求“用户选择记录，即可上传”。据此将主动记录作为独立对话样本入口，沿用参与改进退出偏好、90 天留存和删除控制；无需等待沉淀，覆盖所选记录已有及新增的用户消息和 AI 回复，不额外读取附件、工具事件或推理摘要。当前为源码实现，尚未部署或发布。助手提出的价值判断：此入口可能减少只观察到主动沉淀者的样本偏差，为提取算法提供更早的真实对话材料；覆盖率、样本质量与实际改进收益仍待真实用户试点验证。证据：[记录采集模块](../../src/improvement/recording.ts)、[产品范围](../product.md)。

2026-09-11 界面补充：用户明确上传说明不应每次出现。本轮将记录入口调整为首次说明、成功记录后跨页面和重启不重复，范围说明版本变化再提示；完整范围及关闭、删除仍常驻服务设置。助手的设计判断：将首次知情说明和日常操作分开，可以减少重复打扰，同时保留可追溯的控制入口。此为界面设计与源码状态，尚未部署或发布；是否改善实际体验待用户试用。依据：[记录提示状态](../../src/improvement/recording.ts)。

### 待讨论的验证方法

选择同一类重复工作，用新输入比较“原有方式、普通总结、Worket 确认后的定义”。尽量控制执行者、任务难度与预算，比较交付通过率、返工次数、人工解释与检查时间、总体费用，并保留反例。后续再更换执行者，单独验证迁移能力；避免同时更换模型与定义而混淆收益来源。候选生成、评审、执行和维护成本均计入。

人类确认和真实交付效果承担不同职责：前者确定目标、约束及可接受的取舍，后者检验方法的效用。效果评测不能自动改写业务约定或授权，原始 WorkRecord 也不因短期未提升指标而删除。该设想不改变现有用户主动沉淀的边界，不授权自动训练或扩大采集。

### BP 候选表达与展示场景

方向性表述：**Worket 希望把企业的工作经验变成可复用、可验证、可持续改进的工作资产，让每次沉淀都有后续交付证据。**

展示可选择一类报告：从首份报告的实际修订中确认定义，用不同输入完成后续报告，展示定义版本、返工变化和人工投入。只有取得真实对照证据后，才能表述为 Worket 已验证的优势。MemOp 支持的是评测思路，不能替代企业场景或 Worket 的效果验证。

## B003 — 从理解用户意图到提炼可复用的工作约定

### 2026-09-11 实验复盘补充

讨论起因：用户要求总结昨晚仿照 ToM-SWE 的实验结果与启发。本次核对独立研究分支 `codex/conversation-requirements-research` 的 `ecfd45a` 报告及语义复核；下文为项目实验事实与助手判断，不代表用户批准产品实现。后面的初始设计说明保留为历史背景。

已核实的项目实验事实：使用 DeepSeek V4.1 Flash，20 条自建合成样本及同一用户的 6 项真实工作（3 项开发、3 项初始留出）。v0.9 前瞻评估的正向要求/必要澄清槽位覆盖，合成 direct 为 22/23、grounded 为 23/23，真实分别为 18/19、17/19；模型自动评分存在视频稿件更改的 gold 争议，不能解释为真人准确率或稳定优劣。v0.11 在已见数据上回归改善，但来源复核仍发现两条有效复合要求的确认范围或旧前提错误。四个合成订单任务中，完整会话与提炼要求在程序计算条件下均为 4/4，未显示提炼相对完整会话的额外交付收益。

当前达到的是有原文依据、可供审阅修订的单次工作要求草案；没有完成跨实例泛化、真人确认或真实新工作复用验收。来源位置与哈希校验、15 项程序测试通过属于工程证据，不是语义准确或产品收益证据。完整记录见本机研究工作树的 [研究报告](../../output/research-worktree/docs/research/conversation-requirements-report.md) 与 [语义复核](../../output/research-worktree/docs/research/conversation-requirements-semantic-audit.md)；这些路径为本地研究产物，不承诺在主分支公开浏览时存在。

助手提出的产品洞察与设计方向（待验证）：

- 工作要求在协作中逐步形成，纠正、否定和确认是候选工作约定的重要来源。Worket 可探索帮助用户从已经做过的工作中整理约定，减少事前完整写规范的负担；本实验没有量化这一负担是否下降。
- 提炼的关键是保留用户决定及其变化：目标与实现方法分开、每个命题有证据、旧方案不污染新约定、探索许可不被误作等待定稿。增加一次模型审核并不能保证这些判断正确，过度保守还会丢掉有效要求或制造重复提问。
- 要求明确性与执行可靠性需要分别验证。结构化草案有潜在的检查、交接和复用价值，但必须将生成、审阅、修订及执行成本一起比较，不能用抽取高分代替交付收益。

可展示场景：从真实对话中选取一条初始要求、一次修改与一次确认，展示最终有效约定及原文，再用新输入交给执行者完成下一次工作。下一阶段建议先取得真人核对的同类工作样本，用前两次形成候选、第三次未见记录检查泛化，之后以新输入比较完整会话、普通总结和确认后的工作定义；记录关键约束错误、重复解释、人工修订时间及交付结果。此为验证建议，不是已完成实验或已批准开发。

### 2026-09-11 真人审阅交互落地

用户明确要求补上工作发起人标注，并强调交互应流畅。本轮沿用独立研究边界，实现本地审阅页面，直接载入昨晚 6 份草案的 81 条要求与 5 个待澄清问题。支持逐条接受、原位修改、拒绝、暂放、撤销、原文前后文回查、补遗漏、自动暂存、刷新恢复、显式提交和导出；修改区分历史理解修正与今天的新决定。原实验草案与真人反馈分开保存，不自动发布 WorkDefinition。

助手提出的产品洞察：真人确认是否能成为有效的研究反馈，取决于它是否融入判断本身；连续审阅、随手修改和可撤销的选择有机会降低标注负担，但不能靠默认接受或隐藏不确定性制造高认可率。界面不显示模型评分、gold 或审计结论，避免直接影响用户判断；历史条目仍带有效状态和原文依据。

当前证据：研究分支 `codex/conversation-requirements-research` 的 [真人审阅说明](../../output/research-worktree/docs/research/requirements-human-review.md)；23 项程序测试通过，另用独立 QA 输出目录走完提交、刷新恢复、390 像素窄屏与服务中断重试。测试操作标为 `qa-automation`，未混入真人结果。实际审阅认可率、用户感受与时间成本待用户本人完成；此为研究工具实现，未集成或发布桌面产品。

### 2026-09-11 核心证明点澄清

用户追问：核心是否是“提炼可复用的工作定义，可以帮助 Agent 有更好的表现”？助手建议将主假设具体化为：**从已完成的真实协作中提炼并经用户确认的工作定义，能否在新输入的同类工作中，以更少的重复说明、纠正和检查投入，达到既定交付标准。** 同等投入下交付质量提升也是收益；需同时报告生成、确认、维护、模型执行成本及错误约束，不能只统计下一次执行更快。

证明链分为三层：单次要求是否忠实；换输入后稳定规则是否仍适用且不携带旧客户、答案或临时授权；实际复用是否改善质量或总投入。昨晚实验主要推进第一层，未完成后两层。先固定执行者与任务条件比较完整历史、普通总结和确认后的定义，再更换执行者单独验证迁移，避免将模型能力变化混作工作定义收益。即使交付质量相同，只要总体人力或费用有可重复的下降，也可能支持产品价值；相反，高抽取分数不能单独证明价值。

BP 候选表述（助手提出，待真实复用验证）：让一次协作形成的工作标准，在后续同类工作中继续发挥作用，减少用户反复教会执行者的成本。该表述不是已验证收益，也不表示任意 Agent 均可胜任。

### 讨论起因与用户观点

2026-09-10，用户询问本地运行或复现 ToM-SWE 的机器要求，并明确希望基于该研究，从用户实际对话中提炼 WorkDefinition。这是研究和算法探索方向，不代表批准新增数据采集、训练或改写产品流程。

### 已核实的研究事实

核实日期：2026-09-10。ToM-SWE 以原始会话、单会话用户分析、跨会话用户模型构成三层记忆，为软件工程执行 Agent 提供目标、约束与偏好方面的建议。论文验证的是编码任务和用户建模，并未直接验证 Worket 所定义的可复用工作约定。来源：[论文 v2 第 2 节及附录 A.4](https://arxiv.org/html/2510.21903v2)、[官方代码](https://github.com/OpenHands/ToM-SWE)。

2026-09-11 用户提醒论文包含用户评分/标注后，重新核实 [v2 第 6 节](https://arxiv.org/html/2510.21903v2#S6)：17 名开发者在三周日常工作中，对 ToM 建议选择接受、修改后接受或拒绝；209 次会话出现 174 次建议，完全接受 74.1%，部分接受 12.1%，合计 86.2%。这是实际使用时对建议的反馈标注，不是逐条标注全部历史对话或建立完整要求金标准。研究没有对照组，作者不据此作生产率提升的因果结论。另一个离线实验的 1–5 分满意度来自模拟用户模型，任务解决率由测试判定（第 4–5 节）。因此此前只突出模拟用户评测的概括不完整，应同时呈现真人建议采纳与离线执行评测两条证据。

助手据此补充的验证建议（尚未实施）：Worket 可先让真实工作发起人对要求候选接受、修改或拒绝，并补充遗漏，验证是否理解用户。该阶段可以独立于新工作执行开展；接受率、修改类型和审阅时间形成直接反馈，但不能替代后续跨实例适用性和实际交付收益验证。接受某条本次要求，也不自动代表用户同意它作为长期通用规则。

### 对 Worket 的洞察与当前依据

助手提出的洞察：真实对话中的纠正、否定、验收反馈，可能比孤立的初始指令更能表达工作的真实要求。把这些信息转成可追溯的候选约定，有机会降低用户事先编写工作定义的负担。用户的一般交流偏好、本次工作的例外、同类工作的稳定要求须分别判断；反复出现并不自动成为通用规则。

当前依据：[领域定义](../../CONTEXT.md) 已将 WorkDefinition 与 WorkRecord 区分；[现有提炼流程](../../server/workflow.mjs) 已实现分块提取、纠正关系整合、跨工作泛化和来源校验。当前中间结构保留文本、范围、来源和替代关系，但用户陈述/Agent 提案、确认状态等信息尚未逐项成为独立的中间字段。这提供了一个可实验的改进点，不能据此断言现有真实样本效果已被证明不足。

### 助手提出的设计设想与验证

保留现有工作定义契约，实验性增强“对话证据 → 单次工作要求 → 同类工作共性与变量 → 候选定义”流程。将发言来源、纠正与撤销、适用范围和证据回查显式化；对不确定的泛化提出问题，参考方法默认不升级为强制步骤。最终仍由用户主动沉淀并确认。

在同一模型和相近预算下比较直接提炼、现有两阶段流程、上述增强流程；先评估关键要求遗漏、错误泛化、来源错误和用户修订量，再用未参与开发的同类记录及新输入检验复用。一个小样本只能用于发现问题，不能支持整体效果宣传。

### 用户价值与可展示场景

潜在价值：让用户在正常工作与纠正 AI 的过程中逐渐形成可复用约定，减少重复解释。以客户报告为例，保留“指标必须可追溯”等稳定要求，将客户、日期和数据改为本次输入，并识别“这次先不做竞品分析”为本次例外。展示每个候选条目的对话依据，以及下一次工作的交付效果。

BP 候选表达（方向性）：**Worket 希望把用户在真实协作中表达和修正的要求，转成可确认、可复用、可验证的工作定义。** 其准确率、节省时间和跨执行者收益仍待真实实验；研究笔记见 [ToM-SWE 可行性分析](../research/tom-swe-feasibility.md)。

## B004 — 减少常驻工作入口的屏幕占用

日期：2026-09-11。用户观点：桌宠目前有些占地，希望拖到桌面左、右、上边缘后变成扒住边缘的形态。

当前源码依据：贴边时将原生窗口缩到 32×68 或 68×32，保留状态点与单击打开入口，拖离恢复，后台工作记录独立运行；见 [桌宠位置控制](../../src/desktop/pet-position.ts)。尚未打包发布。

助手提出的设计判断：长期陪伴式入口需要让用户自主决定何时显露、何时收纳，减少遮挡可能提高持续保留应用的意愿。可展示“记录中 → 拖到边缘 → 小头和爪子收纳 → 单击查看工作 → 拖出恢复”的完整场景。实际遮挡感、发现性与留存收益仍待用户试用验证，不能把几何面积缩小表述为已验证的留存提升。

B004 补充（2026-09-11）：用户反馈透明窗口边界影响上方和左侧停留，并希望利用屏幕底边 Dock 两侧空白。当前源码已按可见角色约束位置，加入底部空白吸附；Dock 宽度为保守估算，实际空白利用率待试用。用户提出吸附时只露眼睛，用户已确认并应用 B 双爪偷看造型。设计判断：收纳不仅是缩小角色，还要让角色能停在用户选择的位置。

2026-09-11 用户确认 B「双爪偷看」：四向吸附统一采用小圆头、两只眼睛和贴边爪尖，隐藏嘴巴，露出约 19 像素；保留状态点、点击打开和拖离恢复。原生点击窗口仍为 32×68 / 68×32。

B004 补充（2026-09-11）：用户确认外形后指出底部切换割裂。已复现并修复拖动按工作区、吸附按物理屏幕造成的位置断层，底部通道跟手回归通过。助手设计判断：收纳入口的体验还依赖拖动路径连续，静态造型和最终坐标通过不能代替过程验证；整体主观流畅度仍需用户试用。

2026-09-11 B004 补充：用户明确希望贴边有“被吸进去”的感觉。当前实现加入短吸入、双爪显露和拖出展开，原生回归检查动画中间缩放及结束后清理；主观手感待本机试用。

2026-09-11 B004 补充：用户确认贴边记录状态使用轻微绿色呼吸点，保留后台记录的可感知性，同时让眼睛和双爪静止。源码已实现，整体打扰感仍待试用。

## B005 — 用一致的操作降低工作管理的学习成本

日期：2026-09-11。状态：界面源码已调整，实际易用性收益待用户试用。

用户观点：逐页审查 Worket 的页面、交互和按钮布局，统一混乱的字体与尺寸，采用 Apple 风格的简洁界面，去除解释性内容。

2026-09-11 用户复核：苹果风格指向简洁与一致的操作，并不意味着采用冷白蓝色。用户更喜欢原有暖黄、纸质感，希望区域更小、元素更紧凑，并移除黄色说明横幅。已在源码中调整为 400×660 面板、暖黄纸纹和棕金按钮。助手判断：视觉一致性可以与 Worket 自身的温暖气质并存；体验收益仍待试用验证。

助手的设计判断：把主操作放在稳定的位置，让记录、交接、沉淀、复用和验收共享视觉与操作规则，可以减少用户在理解工作内容之外付出的界面学习成本。复杂度不应通过重复说明转移给用户；实际上传范围和删除后果仍须清晰可查。

当前依据：桌面主面板、沉淀与服务弹窗、桌宠文字和后台使用统一的字体及控件规格；工作详情主次操作分开，重复标题与空栏目清理。证据：[界面验收](../qa/interface-consistency.md)、[面板样式](../../src/renderer/panel.css)、[面板交互](../../src/renderer/panel.ts)。未作竞品事实比较；桌面改动已随 v0.1.2 正式发布，后台页面源码不代表本轮已部署到服务端。

潜在用户价值与展示场景：用户从一项正在记录的工作进入交接，再完成并沉淀，在同一套操作规则下发起下一次工作。BP 候选表达：让工作在不同执行者之间延续时，保持一致的管理体验。

待验证：首次使用能否不依赖讲解完成记录与交接，主操作查找时间是否缩短，误触和反复返回是否减少；当前合成测试不能证明这些收益。

2026-09-11 B005 补充：用户希望减少反复权限弹窗，并收细右侧滚动条。已核实的实现问题是详情轮询同时校验原附件，浏览也可能触发其他 App 数据目录的系统授权。当前调整为浏览只投影已保存资料，主动使用时访问文件；助手判断是权限请求时机也属于交互一致性，应该对应用户的实际操作。证据：`AppService.dashboardWithContext` 与 `test/integrations/app-service.test.ts`；减少打扰的实际收益待用户试用，不代表永久系统授权已经实现。

2026-09-11 B005 补充：用户发现重启后 HIFU 视频工作看起来没有记录最新执行。实时核对显示原会话事件已完整进入来源档案，但后台同步未驱动详情状态提炼。现已把状态更新接入统一同步路径并保存处理进度，详情同时显示最近执行者回复。助手判断：用户能感知到的记录连续性同时要求“已保存”和“当前可见”；记录条数增长不能替代进度展示。依据：`test/integrations/state-sync.test.ts`；此处是记录同步修复，不代表执行者回复已通过验收。

## B006 — 用真实后续执行衡量跨 Agent 交接价值

### 讨论起因与用户观点

2026-09-12，用户指出 Worket 的主要工作之一，是把与一个 Agent 的协作传给另一个 Agent（当前指 Codex 与 WorkBuddy），并担心现有方式只是记录聊天和引用文件、缺少针对交接的特殊整理。用户要求先设计评估传递成本和有效性的方法。本轮不代表用户已批准修改 Handoff Package 或引入新的整理模型。

### Worket 当前依据

源码显示当前实现并非只搬运完整聊天：`HandoffPackage` 已包含八部分 Work State、当前任务、下一步、最新资料引用和来源档案统计；目标执行者通过 `get_work_context` 读取结构化快照，需要核验时可读取 Source Archive 与 ArtifactRef。完整历史不默认放入主 Prompt。证据：[核心类型](../../src/core/types.ts)、[交接快照生成](../../src/core/work-core.ts)、[MCP 读取接口](../../src/bridge/mcp-handler.ts) 与 [现有工作流](../../workflows/record-and-handoff-work.md)。这些实现证据不能证明整理准确、成本更低或后续执行更好。

### 助手提出的洞察与评测设计（待验证）

交接包的长度或摘要可读性不是最终价值；真正需要验证的是：在相同来源、接收执行者、工具和预算下，目标 Agent 是否以更少的用户重复说明、上下文读取与返工，正确完成后续工作。应把成本拆为交接准备、目标端理解读取和误解恢复三部分，把有效性落到首版/最终交付通过、关键约束错误、工作连续性和资料使用。

评测应从同一来源快照配对比较“完整记录直传、当前 Worket Handoff Package、候选精细整理”，并以人工理想包估计上限。每个案例由工作发起人在看到候选包之前确认交接契约，区分必须传递、按需核验、不得继续采用的旧信息和确需新决策的问题，防止把合理澄清误算成传递失败。详细方法见 [交接成本与有效性评估方法](../design/handoff-evaluation-method.md)。

### 用户价值与 BP 候选表达

潜在用户价值：换 Agent 时不必从头解释，也不必把所有历史都塞给新 Agent；目标执行者取得足以继续工作的上下文，同时保留按需核验来源的能力。该价值尚未通过真实对照实验验证。

BP 候选表达（方向性）：**Worket 希望把跨 Agent 交接从“搬运聊天”变成可度量的工作连续性：减少重复说明与返工，同时让下一位执行者依据真实记录继续完成工作。** 在取得真实配对结果前，不能表述为已降低成本或提高成功率。

### 可展示场景与待验证事项

在同一项有多轮对话和多个资料的真实工作上，于固定接力点分别交给新的 Codex 或 WorkBuddy 会话。展示目标 Agent 首次采取的动作、是否误用旧决定、读取了哪些来源、用户补充了多少次，以及最终交付是否通过，而不只展示生成出的交接摘要。

待验证：两个交接方向是否一致；长对话与短对话的收益差异；资料多时按需检索是否真的节省总 token；结构化提取错误是否比原始直传更危险；准备整理所增加的模型成本能否被减少的重复说明和返工抵消。

2026-09-12 本机样本盘点补充：经用户提出数据量疑问后，助手只聚合本机元数据，不输出标题、正文或工作路径。当前 Codex 共发现 5 份会话文件，其中只有 1 份达到长案例规模（18 个执行轮次、19 条用户消息、48 条助手消息、150 个工具事件、13 个图片输入），其余为 1–3 个执行轮次；Windows 本机未发现可直接用于本轮实验的 WorkBuddy 会话库。判断：这些数据足够走通评测和做单案例诊断，不足以证明一般性的跨 Agent 收益或比较两个方向。同一长会话的多个截止点不能当作多个独立真实工作。建议先完成单案例方法校准，再由用户主动选择自然发生的交接逐步积累；合成样本只用于边界覆盖。详细记录见 [评估方法第 10 节](../design/handoff-evaluation-method.md#10-本机数据就绪度与分阶段启动)。

2026-09-12 公开数据补充：用户询问能否从网上取得足够实验素材。已核实 [SWE-smith Trajectories](https://huggingface.co/datasets/SWE-bench/SWE-smith-trajectories) 数据卡描述 5,017 条带任务、轨迹、补丁和解决状态的模型生成编码轨迹（MIT）；[ThoughtWorks Agentic Coding Trajectories](https://huggingface.co/datasets/thoughtworks/agentic-coding-trajectories) 汇总 15,000 个编码会话与 618K turns，但逐行受上游许可约束；[WebLINX](https://mcgill-nlp.github.io/weblinx/) 有 2,300 个多轮 Web 导航演示和约 100K 次交互，许可为 CC BY-NC-SA 4.0；[WildChat-4.8M](https://huggingface.co/datasets/allenai/WildChat-4.8M) 当前公开非有害内容版本为 3,199,860 份真实对话，许可为 ODC-BY，“4.8M”指完整原始版本规模。助手判断：数量足够建立机制基准，但公开集缺少 Worket 用户在 Codex/WorkBuddy 间真实接力的人工时间与验收，不能直接证明产品降低成本。公开轨迹里的隐藏推理不得进入 Worket 来源，数据污染、敏感内容与许可须单独控制。详细方案见 [评估方法第 11 节](../design/handoff-evaluation-method.md#11-公开数据的补充方案)。

2026-09-12 WildChat 适配性复核：用户指出此前列出的公开数据中只有 WildChat 略符合真实聊天要求。已核实原始论文的数据来自用户明确同意后使用的免费 GPT-3.5/GPT-4 API 聊天站点，并非 ChatGPT 官方产品导出；原始 1M 论文版本平均 2.52 轮，约 41% 为多轮、3.7% 超过 10 轮，说明长工作对话只占少数但绝对数量仍可筛选。数据有完整用户/助手文本、语言、模型、轮数和时间等字段，但没有附件、工具状态、Agent 切换、满意度或交付验收。助手判断：可在对话中间插入模拟交接点，以后续真实用户消息检查新 Agent 是否延续目标、约束与修正；原回复只能作参考而非正确答案。该实验测的是“上下文表示是否足以继续对话”，不是 Worket 完整交接收益。隐私上不使用国家、州、哈希 IP 与请求头，优先排除已脱敏条目和敏感内容，不将正文提交仓库；公开清洗版仍不能视为零隐私风险。

2026-09-12 跨模型实验设计补充：用户明确，实验不能局限于 Codex/WorkBuddy 应用，还要先控制接收模型能力差异。用户建议在约 9 轮长对话的第 7 或第 8 轮切开，将工作交给新的、最好是中国境内易取得 API 且与 GPT-4o 能力相近的模型；第一层比较换模型后与未移交结果的差异，第二层才比较交接方法。核实后纠正：WildChat 不是 GPT-5.3/5.4 数据，4.8M 版本包含 GPT-4o、GPT-4.1-mini、GPT-3.5、GPT-4、o1 等，应只选 GPT-4o 子集。助手最初提出 `GLM-4-Plus`，用户进一步检查当前模型总览后质疑其可用性；复核发现它虽有旧说明页，却不在智谱当前全部文本模型清单中，不能据此声称仍受支持。首选因此改为阿里云百炼当前模型清单及独立页面均列出的 `deepseek-v3`：中国北京地域 API、65,536 上下文，初代 V3 发布时厂商将其定位在 GPT-4o/Claude 3.5 Sonnet 能力带；这仍须用完整历史条件校准。新增原则：候选资格须同时通过“当前模型清单 + 实验账号最小调用”，旧文档或榜单不等于服务可用。评测分解为 `模型差异 = 同一接收模型完整历史结果 - 原 GPT-4o 历史回复`、`交接损失 = 完整历史结果 - 某方法结果`、`方法增量 = 新方法结果 - 当前 Worket 结果`，避免把模型与方法混为一个效应。完整设计见 [WildChat 跨模型交接评测方案 v1](../design/wildchat-handoff-evaluation-v1.md)。

## B007 — 跨桌面平台保持同一工作对象与交接体验

### 讨论起因与用户观点

2026-09-12，用户提出构建 Windows 版本的 Worket。用户没有提出新的领域实体或改变现有记录授权边界；需求指向让同一套工作记录、沉淀与交接体验覆盖 Windows 用户。

### Worket 当前依据与已实现状态

本轮已将 Electron 桌宠与轻量面板打包为 Windows x64 便携包，增加 Win32 前台窗口识别、Codex Windows App Server 路径、WorkBuddy 命名管道、Windows 文件路径处理、托盘入口，以及按平台选择更新附件。117 项自动测试、打包后真实 Electron 窗口与合成更新下载验收通过。项目证据：`src/adapters/foreground/windows-context.cs`、`src/adapters/codex/app-server-client.ts`、`src/adapters/workbuddy/desktop-client.ts`、`scripts/package-desktop.mjs` 和 `scripts/release-win.mjs`。

当前证据证明 Windows 应用壳、核心本地逻辑、合成更新链和 Codex 会话选择后的真实历史导入可用；尚未在 Windows WorkBuddy 上完成真实聊天读取，也未完成 Windows 双向交接及重启续录。因此不能把“Windows 与 macOS 功能完全等价”写成已验证事实。当前便携包未做 Windows 代码签名，公开下载可能出现 SmartScreen 来源提示。

2026-09-12 安装验收补充：从 `%LOCALAPPDATA%\Programs\Worket\Worket.exe` 启动后，Windows Codex App Server 的真实会话列表、用户明确选择后的历史导入、工作完成与面板重开已通过，测试使用临时数据库且未上传内容。Win32 窗口只返回通用 `ChatGPT` 标题时不能精确定位当前任务，Worket 会进入会话选择而不猜测。Windows WorkBuddy 与跨执行者接力仍未验证，因此跨平台完整价值继续标记为待验证。

### 助手提出的洞察、用户价值与展示场景

潜在价值不只是增加一个安装包，而是让 Work Object 不再绑定某一桌面操作系统：用户换设备或团队成员使用不同系统时，工作身份、来源追溯与交接约定仍保持一致。BP 可展示同一 WorkInstance 在 macOS 与 Windows 客户端使用相同结构和执行者协议，但在真实跨平台闭环完成前应表述为产品方向。

待验证：Windows Codex / WorkBuddy 实际进程身份和窗口标题稳定性；WorkBuddy 内部扩展在 Windows 版本中的权限与生命周期；命名管道的多用户隔离；DPAPI 凭据保存；高 DPI、多屏、任务栏位置、休眠恢复；无代码签名对安装转化和信任的影响。
