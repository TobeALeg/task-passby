# WorkDefinition 提取：执行依据与首轮计划

日期：2026-09-09。用途：将公开调研转化为 Worket 下一步可以执行和验收的工作。本文规定首轮试点的建议路线、交付物、分工与判断门槛；不是已经完成真实质量验证的声明，也不改变已发布定义或当前产品行为。

## 1. 执行决策及依据

**首轮采用“有依据的工作约定 + 可替换的参考方法”，沿用现有七类定义内容，以真实案例建立自己的提取评测。** 公开 benchmark 提供任务与评价设计；本地真实需求决定可复用内容。

| 决策 | 外部依据 | 对本项目的具体执行选择 |
|---|---|---|
| 先明确输入、交付、条件和验收，再整理方法 | [IDEF0](https://nvlpubs.nist.gov/nistpubs/Legacy/FIPS/fipspub183.pdf) 分离输入、输出、控制条件和机制；[CMMN](https://www.omg.org/spec/CMMN/1.1/PDF) 支持目标、资料与运行中规划 | 沿用目的、输入、交付、约束、验收、方法、资料七类；适用范围先写入目的或约束 |
| 历史步骤不自动成为强制步骤 | [τ 官方评估说明](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)把参考动作和目标终态评分分开 | 方法默认参考；必需步骤须有业务要求、明确依赖或用户确认；审批等过程义务单独验收 |
| 从记录形成候选，再用新实例验证 | [AWM](https://arxiv.org/html/2409.07429v1) 研究经历中的子流程抽象与后续使用 | 从同类记录对照输入角色、稳定要求与例外；保留来源及未决事项 |
| 评价允许多种合理的定义 | [τ 的不同操作路径](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)可以达到相同的合格结果；[流程挖掘](https://www.tf-pm.org/upload/1580737614108.pdf)讨论拟合、精确、泛化和简洁的平衡 | 标注必须保留、禁止继承、适用条件、可接受变体及缺口；不用唯一范文的文字相似度评分 |
| 将学习材料与验收材料分开 | [SWE-bench](https://arxiv.org/html/2310.06770v3) 区分初始问题、环境与参考解法，并控制后见信息 | 留出任务只向执行端提供开始时可见的输入；后续修改和旧答案只用于评审 |
| 先小规模诊断，再扩大验证 | 这是本地资源与产品阶段的选择，文献没有证明某个样本数足够 | 首轮一类工作、两份提取记录、一份留出记录；再验证新的实际工作，之后扩展到其他类别 |

七字段的数量、试点规模及以下门槛属于本项目的工程选择，仍需真实案例检验。当前依据支持先执行这条路线；没有证据支持预先承诺准确率、节省比例或跨行业泛化能力。

## 2. 首轮的可验收结果

完成首轮时应交付：

1. 一组范围清楚、来源可核查的同类工作记录，以及哪些记录用于提取、哪些留出的清单。
2. 一份逐条标注的业务要求依据表；模型候选、人工修改和确认版本可以相互追溯。
3. 一份在新输入下实际执行过的 WorkDefinition，以及对应的交付物、逐项验收结果和过程义务证据。
4. 一份对比报告，说明当前提取器哪里会错、改动是否改善、用户是否减少重复说明与返工。
5. 一个有证据的后续决定：继续扩大、针对明确问题再改一次，或暂缓把这类工作沉淀为定义。

定义生成成功、接口连通和 JSON 合法，分别只能证明相应技术环节可用。用户保存定义是采用行为，实际复用和交付验收用于判断效果。

以下来自 2026-09-09 对当前代码和验收记录的核对。

| 环节 | 当前证据 | 下一步工作 |

| 来源、候选、人工修改和验收采集 | [improvement.mjs](../server/improvement.mjs)、[采集验收](acceptance/worket-improvement.md) 已有 | 利用现有范围授权与样本生命周期组织试点评审；备注尚不是结构化评测结果 |
| 新输入与外部执行 | [work-package.ts](../src/definitions/work-package.ts) 及现有桌面复用链已有 | 用真实工作验证，保留执行与验收证据 |
| 供应商接入 | [后台验收补充](acceptance/worket-backend-admin.md) 已记录用户完成配置及固定文本连通 | 执行时由助手核对既有配置和接入；本轮只读请求未连通默认本机 `/health`，尚未验证当前服务状态 |

一个需要重点观察的信息传递风险：分块阶段要求返回 `id/text/scope/sourceKeys/replacedBy`，聚合阶段收到这些中间结果，不直接收到原始事件全文。当前中间结构没有强制携带每项的发言角色、精确摘录及条件信息。应检查这是否造成角色混淆或条件遗漏；这是从代码发现的待验证风险，不能在没有案例的情况下宣称已经导致失败。

现有复用改进采集仅含定义、非文件输入、验收及选中的交付 ID，没有新执行对话或交付正文。首轮效果检查需要用户指定可检查的实际交付范围；不把文件 ID 当作已经看过成果的证据。

## 4. 可以直接执行的提取规则

工作候选的粒度是“可以独立布置并独立验收的一项结果”。一个会话可包含多项工作，同一事项也可跨多个会话。第一轮由助手整理、用户裁定不清楚的边界，暂不依赖新的自动切分功能。

| 记录证据 | 默认处理 | 必须避免 |
|---|---|---|
| 明确的长期要求，如“以后这类报告每条事实都要有来源” | 作为可复用要求候选并保留原文依据 | 只保留链接而不检查其是否支持要求 |
| 本次客户、材料、期间或地区 | 根据业务角色判断是否成为每次输入 | 把旧值作为新任务的隐式默认值；把本来固定的适用条件任意参数化 |
| “这次赶时间，暂时不做……” | 保留为本次例外；是否形成可选项待确认 | 推导为长期省略该项 |
| 同一工作中的明确修正、取消 | 记录替代关系；以有效要求构造候选 | 按出现次数决定重要性；跨不同工作用后来的要求覆盖此前要求 |
| Agent 建议、尝试路径、未确认的新要求 | 保持提议或参考方法的身份 | 把“好的，继续”解释为确认整段建议 |
| 有明确批准要求或先后依赖的环节 | 保留过程义务，注明触发条件与验收证据 | 仅凭最终结果正确就判定过程合格 |
| 多条记录目标相同但条件不同 | 解释为输入、适用条件或待确认差异 | 只取模糊交集；无依据地把冲突合并成统一规则 |
| 缺少文件正文、完成证据或业务依据 | 暴露具体缺口，给出有标记的提案 | 伪造来源或靠模型常识补成用户要求 |

处理顺序为：固定范围 → 恢复每项工作的有效要求 → 对照同类实例 → 参数化和处理条件 → 生成七类候选 → 检查来源与缺口 → 用户确认 → 新实例验证。

## 5. 评审口径：先有要求依据，再看生成结果

助手先根据提取用记录预填下表。用户只需裁定没有证据可唯一确定、且影响业务结果的事项，无需从头写标准答案。

| 标注类别 | 应填内容 | 判定方式 |
|---|---|---|
| 必须保留 | 目的、交付、关键约束及其来源、是否关键 | 候选是否以等价含义完整表达 |
| 禁止继承 | 旧客户、旧结论、已撤销要求、临时授权等 | 候选是否错误固定或默认带入 |
| 输入与条件 | 每次变化的角色、固定范围、条件差异 | 是否能正确实例化，而非仅替换名词 |
| 可接受变体 | 允许不同表述、工具、参考路径或拆分 | 不因与某份范文不同而误判 |
| 证据不足 | 尚不清楚的事项、影响及需要谁裁定 | 是否显式提出，而非静默编造 |
| 验收证据 | 结果检查、指定材料、实际确认或批准事件 | 能否据此判定通过、退回或未验证 |

每个判定至少保留：要求编号、来源位置、期望类别、是否关键、候选对应位置、通过／失败／未决、原因和评审人。引用 ID 存在属于结构检查，引用是否实际支持主张属于语义检查。

原始模型候选与用户修订后的定义分别评分。人工修正可以形成可用版本，但不能把原候选的错误改记为自动提取通过；修正所需的人力计入成本。

错误按 `资料缺失 / 工作边界错误 / 提取遗漏或误读 / 参数化错误 / 实例填参错误 / 执行器错误 / 工具环境故障 / 评价不确定` 分开记录。必要时用人工确认后的定义复跑定位；单次复跑仍有随机性，不能据一次成功直接断言原因。

## 6. 执行顺序、责任与完成条件

| 工作包 | 助手负责 | 用户负责 | 完成条件 | 当前状态 |
|---|---|---|---|---|
| P0 执行依据 | 查一手资料、形成决策、规则、评审表和差距清单 | 无需再读论文或自行设计框架 | 本文可单独支撑首轮准备 | 本轮完成 |
| P1 选样与业务标注 | 整理指定记录、关联纠正和结果、预填依据表、提出候选 | 指定一类值得反复做的工作及材料范围；裁定少量关键歧义 | 两份提取材料、至少一份留出材料及已裁定的要求依据表 | 等待选定真实记录 |
| P2 固定基线与评测工具 | 接通既有模型配置；补真实案例入口、评审判定和版本对比；运行基线并给出错误清单 | 仅在凭据确实无法使用时完成登录／密钥操作；确认有歧义的业务评分 | 可复跑同一输入并逐项解释结果，记录模型／提示／代码／输入版本及用量 | 待执行 |
| P3 有针对性的提取改进 | 按错误修改提示、证据传递或局部流程；完成功能后集中验证、独立本地提交 | 仅当修正改变业务约定时裁定 | 关键错误消除，未引入新的关键遗漏；没有错误则不为改而改 | 由基线结果决定 |
| P4 新实例复用 | 组装新输入工作包、操作受支持执行端、收集交付与证据、完成对照及归因 | 给出真实下一项需求及执行范围；确认交付是否可用 | 新实例真实交付，逐项验收，报告人力和执行成本 | 等待新需求与前置验证 |
| P5 扩大或调整 | 汇总证据，给出继续／修订／暂缓建议；通过后扩至三类工作 | 决定下一类是否值得投入 | 结论与数据范围匹配，列明未验证条件 | 待首轮结论 |

P1 与 P2 中不依赖真实正文的准备可以并行。当前请求交付的是研究与执行依据；表中的代码改进、真实模型调用和外部工作尚未执行。确定进入首轮后，常规整理、标注和技术步骤由助手持续完成，不逐步要求用户操作。

### 评测工具的最小交付边界

在既有评测脚本和样本链上补齐以下能力即可支撑首轮：

- 显式选择案例及提取／开发／留出用途，禁止默认读取全库；每次记录来源快照和版本。
- 逐例记录原始候选、人工修改和业务判定，支持“未决／无法评分”，没有完成语义评审时不显示质量通过。
- 比较固定基线和一个候选版本，保留每条要求及错误变化、调用次数、耗时和用量。
- 接入已有配置时不打印或要求用户粘贴密钥；当前评测脚本的环境变量入口与后台配置分开，由助手处理适配。
- 正文、标注和派生评测材料遵守原范围及留存、删除约定。首轮优先在现有私有样本生命周期内审阅，若新增副本则必须同时实现删除和到期清理，正文不提交 Git。

优先改动位置为 `server/evaluate.mjs` 及评审连接层；只有错误证据指向提取本身，才改 `server/workflow.mjs`。若发现长记录聚合丢失角色或条件，先补强中间证据和定向来源回读，再判断是否需要新增模型阶段。最终定义结构需要变化时，另行说明真实案例要求，不能仅为了字段齐全而扩张。

## 7. 两道验收门槛

**G1：可以进入真实复用。** 在已裁定的评测案例中，关键要求无遗漏，伪造来源、错误归属、旧客户／答案污染和临时授权固化等关键错误为零；影响执行和验收的歧义已解决；未验证项明确保留。用户确认候选版本。这是项目首轮门槛，不代表总体错误率为零。

**G2：这类定义值得继续投入。** 在新的真实任务中按预先确定的标准完成交付，关键过程义务也有证据；相对通常重新布置方式，重复说明或返工至少有一项可观察改善，且验收质量不降低。如果没有可靠基线，则只记录此次交付与成本，效用保持“未证明”，不能直接宣称节省。

对照至少记录：候选审阅时间、本次填参时间、澄清轮数、用户修改／返工时间、执行时间、模型用量、逐项验收结果。首次整理成本也要计算；一次复用只证明在该范围可行，持续净收益需要后续观察。

对照规则：

1. 固定模型版本、工具、初始环境、必要资料、资源预算及验收标准；不同执行条件单独记录。
2. 历史留出只向执行器提供当时可见的输入。后续纠正、最终产物和评价答案不提前进入其上下文。
3. 第三份记录一旦用于发现错误并调整提取器，就改列开发材料；修正版另用第四份未见记录或新的前向工作验证。
4. 比较“通常的重新布置方式”与“确认定义加新输入”。通常布置可以包含业务上必须的资料与规则；不得故意删掉关键要求制造弱基线。
5. 审批、确认等义务检查执行前的主体、范围、时间及对应操作。结果成功不能替代过程证据。
6. 使用独立评审条件判断候选；模型可辅助，但不能仅让生成模型自评。小样本逐例报告，不能包装为稳定的总体提升百分比。

如果 G1 失败，先修有证据的提取问题；如果 G1 通过而 G2 失败，区分定义价值不足、输入缺口、执行器能力及环境故障，按原因调整。若多次复用仍无可观察收益，保留工作记录并暂缓为该类别维护定义。

## 8. 用户实际需要投入的事项

用户负责四项业务判断：**选值得复用的工作、确定记录使用范围、裁定长期规则或例外、确认新交付是否可用。** 数据整理、要求标注、候选编写、提示设计、程序修改、测试、对照及报告由助手完成。用户无需提供整理好的 JSON、完整标准答案或重新研究 benchmark。

启动时只需指出一类工作和两至三条记录的位置或名称；可以先有两条历史记录，把下一次真实工作作为未见验证。材料齐全程度由助手检查，必要时再定向补充。真实调用前呈现所选记录／附件范围并沿用已确认的处理与留存选择；已有授权不重复询问，新范围不从旧授权推定。

后台配置曾经完成，优先恢复并检查既有服务；是否需要用户重新登录或填凭据，由当时实际状态决定。任务若涉及发布、付费购买、删除或联系第三方，执行范围应具体到相应操作，正常分析和整理不需要用户代做。

## 9. 一手来源

- [S1 NIST：IDEF0 / FIPS 183，§3.2.2.1](https://nvlpubs.nist.gov/nistpubs/Legacy/FIPS/fipspub183.pdf)：历史功能建模方法，本文借鉴结构分离，不视为当前强制标准。
- [S2 OMG：CMMN 1.1，§4.1–4.2](https://www.omg.org/spec/CMMN/1.1/PDF)：目标、资料、运行时规划，以及由执行经验改进案例模型。
- [S3 τ 系列官方：Task Schema and Evaluation](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)：目标终态与参考操作的关系；本文依据该文档说明，不混用不同版本成绩。
- [S4 Agent Workflow Memory，§2、附录 A](https://arxiv.org/html/2409.07429v1)：经历中的子流程抽象、参数化及后续使用；不直接等于完整业务定义。
- [S5 Process Mining Manifesto，C5–C6](https://www.tf-pm.org/upload/1580737614108.pdf)：有限日志、过拟合及多种质量维度的平衡。
- [S6 SWE-bench 原论文，§2、附录 A](https://arxiv.org/html/2310.06770v3)：真实问题实例、初始环境、参考修复与测试的分离。

本文所列执行流程、样本数量、成本口径和 G1/G2 门槛为基于上述来源及当前代码提出的本地方案，效果需要按首轮计划验证。
